# DLD Kit 1.0 — Implementation Plan

**Status:** high-level plan. This document sets direction and scope for 1.0. The individual choices get recorded as decisions in dld-kit's own decision log as each workstream starts; where a decision and this document disagree, the decision wins.

## Goal

Ship DLD Kit 1.0 as a **TypeScript CLI and library published to npm**, with the skills distributed through the channels agents actually use today. Replace the bash helper scripts and the hand-synced dual skill directories with one implementation and one source of truth.

## Scope

**In 1.0**

- The core DLD skills that exist on `main` today: init, decide, plan, implement, adjust, lookup, status, audit, audit-auto, retrofit, snapshot, reindex.
- A `dld` CLI and library that replaces every script under `skills/*/scripts/`.
- Generated per-harness skill output from one canonical source.
- Distribution via npm, `npx skills`, and a Claude Code plugin marketplace.

**Not in 1.0**

- `/dld-run` and the harness extensions (pi, OpenCode). That work lives on the `dld-run` branch and ships after 1.0, once the extensions have had enough manual testing to feel polished. Its decision log (DL-001..DL-024 on that branch) is not carried over; if the work resumes, it is rebased onto 1.0 and reindexed with `/dld-reindex`.
- Tessl as a distribution channel (see [Distribution](#distribution)).
- Native single-file binaries (Bun `--compile`) and Homebrew.

## Distribution

**Runtime:** Node 20+ is the supported runtime. Bun is a development tool (test runner, scripts) only; nothing shipped may require it.

## Architecture

### One source, generated output

Canonical skill templates are the single source. A build step generates:

- `skills/` — committed, conventional layout, consumed by `npx skills`, `gh skill`, and the plugin marketplaces.
- Per-harness variations (frontmatter fields, script invocation, paths) through a small adapter registry, following OpenSpec's pattern.

`dld init` / `dld update` use the same generator to write skills into a project when a user installs via npm rather than a marketplace.

The hand-maintained `.claude/skills/` copy goes away as a source. A parity test fails the build if committed `skills/` output drifts from what the generator produces. Every generated file carries the version that produced it, so `dld update` can detect stale and orphaned files.

### How skills reach the TypeScript code

Skills installed through a marketplace or `npx skills` arrive without an npm install, so they cannot assume `dld` is on `PATH`. The build therefore bundles the CLI into a single zero-dependency ESM file shipped inside the skills (e.g. `skills/dld-common/scripts/dld.mjs`), invoked with `node`. Skills prefer a `dld` on `PATH` when present and fall back to the bundled file. Skills do not call `npx -y` (slow per call, needs network, awkward to permission-allowlist).

### The always-on rule

The steering rule (look up `@decision` annotations before modifying code, never contradict a decision silently) is the one piece no distribution channel carries. Open question for its own decision: a managed block in `CLAUDE.md`/`AGENTS.md` written by `dld init`/`dld update`, a `SessionStart` hook in the Claude plugin, or both. Note that OpenSpec has moved away from marker blocks.

### Proposed repository layout

```
src/
  core/        # library: config, paths, ids, index, status, records,
               # annotations, audit, snapshot, reindex — pure functions + injected fs/git
  cli/         # `dld` command surface, thin over core
  generate/    # template rendering + per-harness adapters
templates/     # canonical skill sources (SKILL.md templates, rule text)
skills/        # GENERATED — committed for skills.sh / marketplaces
.claude-plugin/
tests/
decisions/     # dld-kit's own decision log (fresh for 1.0)
```

Exact layout and the CLI command surface are decisions to record in their workstreams.

## Porting strategy

The scope on `main` is 22 bash scripts (~1,600 lines) and 166 bats tests. The bats suite is a black-box specification of script behaviour, which makes the port well suited to agent-driven implementation:

1. Stand up the CLI skeleton and a shim so the bats tests can run against `dld <subcommand>` instead of the script.
2. Port script by script (shared utilities first), keeping output formats identical so existing SKILL.md instructions keep working. The bats suite stays green at every step.
3. Once every script is ported, switch SKILL.md templates to call the CLI, delete the bash scripts, and replace the bats suite with bun unit tests against `core` plus a thin set of CLI integration tests.
4. Only after parity: clean up output formats and command naming where the bash-era shapes are awkward.

## Workstreams

Ordered by dependency. Each becomes a decision group (via `/dld-plan`) and one or more stacked branches.

0. **Dogfooding bootstrap.** `/dld-init` on `v1`, fresh decision log, `PRACTICES.md`.
1. **Toolchain.** `package.json`, TypeScript config (Node 20 target, ESM), bun test, typecheck and CI for both suites, npm publish dry-run.
2. **Core + CLI skeleton.** Config reading, project-root and path resolution, CLI dispatch, the bats shim.
3. **Port: common + init + decide + implement.** The operations every workflow touches.
4. **Port: audit + snapshot.**
5. **Port: reindex.** Git-heavy; the riskiest port, done last with the most test coverage.
6. **Generator.** Canonical templates, adapter registry, generated `skills/`, parity test; retire the `.claude/skills/` copy and Tessl packaging.
7. **Skills switch to the CLI.** Bundled `dld.mjs`, PATH-first invocation, bash scripts and bats suite removed.
8. **`dld init` / `dld update`.** Project setup through npm, version stamps, stale-file pruning, the always-on rule mechanism.
9. **Distribution.** Claude plugin marketplace manifest, `npx skills` verification, optional Codex/Cursor manifests, npm publish pipeline.
10. **Docs and release.** README install paths per channel, migration notes for existing copy/Tessl users, 1.0.0.

Workstreams 3–5 can proceed in parallel once 2 lands.

## Branch workflow

- `v1` is the integration branch for 1.0 and starts from `main`.
- Each workstream's decisions are planned and implemented on stacked branches whose PRs target `v1` (or the branch below them in the stack).
- `v1` merges to `main` for the 1.0.0 release.
- `dld-run` holds the paused run/extension work and does not merge into `v1`.

## Appendix: research notes

Summary of the September 2026 distribution research.

- **SKILL.md is a common format.** Around 45 harnesses read Agent Skills. Claude Code reads `.claude/skills/`; most others (Codex, Cursor, pi, Copilot, OpenCode, Antigravity) read `.agents/skills/`.
- **`npx skills` (vercel-labs/skills) dominates installation.** Roughly 7.5–9M npm downloads a week, 70+ supported agents, and automatic listing on the skills.sh leaderboard. `gh skill install` (GitHub CLI 2.90+) is a second channel with version pinning.
- **Plugin marketplaces are per-harness, but one repo can serve several** with a shared `skills/` and a thin manifest per harness. obra/superpowers ships this way with no CLI at all. Copilot CLI reads `.claude-plugin/marketplace.json`. The vendor-neutral Agent Plugins spec (Aug 2026) has only partial Claude Code support.
- **Comparable toolkits.** OpenSpec (npm CLI plus a Homebrew formula depending on `node`; about 40 per-harness adapters from one template source; `openspec update`; parity test against its skills.sh output) is the closest model. BMAD is moving from its own installer to skills.sh and marketplaces. Spec Kit ships every script in sh, ps and py, which a Node CLI avoids.
- **Tessl.** No public install numbers found; its distinguishing feature is eval and security scoring.
- **Bun single-file binaries** were about 99 MB each across 5–8 targets, plus code-signing overhead. Not justified for a small file-manipulation CLI.
