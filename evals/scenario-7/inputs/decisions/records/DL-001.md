## Context

We are building a user-facing productivity application that needs to support real-time updates and scale to multiple concurrent users. We evaluated monolithic, microservice, and serverless architectures.

## Decision

We will build the backend as an event-driven microservice with a REST API surface. The service publishes domain events to an internal event bus; downstream consumers react asynchronously. The public API layer remains synchronous and stateless.

## Rationale

Event-driven architecture decouples producers from consumers, enabling independent scaling and easier addition of new features. REST is well-understood by frontend teams and supported by existing tooling. A single microservice boundary is sufficient at this stage — we avoid premature decomposition while keeping the door open for extraction later.

## Consequences

- Frontend communicates via REST; real-time updates delivered via WebSocket subscriptions to event streams.
- New features that need to react to domain events can subscribe to the bus without modifying existing code.
- Operational complexity increases slightly compared to a pure monolith; we accept this trade-off.
