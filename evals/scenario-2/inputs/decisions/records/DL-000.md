## Context

The codebase handles several distinct processing tasks: parsing, transforming, and emitting records. Early on, all of this logic was co-located in a single module, making it hard to test individual steps in isolation and difficult for contributors to locate where to make changes.

## Decision

Each processing module in `src/` is responsible for exactly one transformation stage. Modules must not call into other modules' internals — they accept well-defined inputs and return well-defined outputs. Cross-cutting concerns (logging, error handling) are handled by utilities in `src/utils/`.

## Rationale

Single-responsibility modules are independently testable, replaceable, and easier to reason about. This constraint also makes the data flow explicit — you can read the pipeline top to bottom without following call graphs between modules.

## Consequences

New processing stages require a new module; they may not be bolted onto an existing one. Any deviation from this pattern must be recorded as a new decision that supersedes this one.
