# Database Schema Approach for Orders

## Context

The orders service needs to persist order data including line items, shipping address, and payment details. Multiple team members have proposed different persistence strategies during the initial design phase. We need to align on one approach before development begins.

## Decision

We will use a normalized relational schema across multiple tables to represent order data. The core tables will be `orders`, `order_items`, `addresses`, and `payment_records`. Foreign key constraints will enforce referential integrity between them.

## Rationale

A normalized schema gives us full SQL query capability, supports transactional integrity across related records, and integrates cleanly with our existing PostgreSQL infrastructure. It also makes it straightforward to add indexes for common query patterns as usage grows.

## Alternatives Considered

### JSON Columns Approach

We evaluated storing order line items and shipping addresses as JSON columns inside a single `orders` table. This approach would reduce the number of tables and simplify reads for the common case of fetching a full order.

However, JSON columns make it difficult to query or index individual fields within the stored data. Enforcing schema on the JSON content requires application-level validation, and migrating the shape of stored JSON is significantly harder than altering typed columns. The flexibility of JSON is not needed here because the structure of orders is well-understood and stable.

For these reasons, we decided not to use JSON columns as the primary storage mechanism for order data.

## Consequences

- We will maintain four related tables with foreign keys.
- All writes to order data must go through transactions to keep tables consistent.
- Query complexity increases slightly compared to a single-table approach, but this is acceptable given the tooling available.
