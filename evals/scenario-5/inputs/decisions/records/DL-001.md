## Decision

All payment operations are exposed as RESTful HTTP endpoints under the `/v1/payments` base path. Each resource follows noun-based URI design: `POST /v1/payments` to initiate a payment, `GET /v1/payments/:id` to retrieve status, and `POST /v1/payments/:id/refunds` for refunds. The API version is embedded in the path to allow breaking changes without disrupting existing integrations.

## Rationale

Versioned REST endpoints give integrating clients a stable contract. By encoding the version in the path, we can ship v2 changes while v1 remains live. Noun-based URIs with HTTP verb semantics are universally understood and trivially cacheable by CDNs.

## Consequences

All new payment resource types must follow this pattern. HTTP method semantics (idempotency of GET, non-idempotency of POST) must be respected when adding endpoints.
