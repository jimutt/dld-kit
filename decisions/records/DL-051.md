## Context

`npx skills add jimutt/dld-kit` (vercel-labs/skills, 1.7.0 in September 2026) and `gh skill install` (GitHub CLI 2.90+) install from the committed `skills/`.

`npx skills`:

- **Discovery.**
  - It looks in the root `SKILL.md`, then `skills/`, then about 30 agent directories, including `.claude/skills` and `.agents/skills`.
  - It deduplicates by frontmatter `name`, so the portable `skills/` wins over this repository's `.claude/skills/`. The claude-code copy of dld-common has no SKILL.md, so it is never found.
- **Internal skills.** A skill with `metadata.internal: true` is left out of default installs, `--all` and `--skill '*'`.
- **Where it installs.**
  - A project install copies each skill's whole directory, keeping file modes, into `.agents/skills/<name>/`, and records it in `skills-lock.json`.
  - For Claude Code, when `.claude/` exists, it adds `.claude/skills/<name>`, a relative symlink to that copy.
  - `--skill` installs a subset, and nothing makes dld-common a dependency of the others.
  - `../dld-common` resolves from a skill as long as dld-common was installed next to it.

`gh skill install`:

- It discovers `skills/*/SKILL.md`, `plugins/*/skills/*` and nested `skills/` directories.
- It installs into `.agents/skills`, or `.claude/skills` for Claude Code.
- It writes files as 0644, which is harmless because the skills run `node`.
- By default it installs the latest release tag.

Two problems follow for dld-kit:

- `dld update` finds installed layouts from existing `dld-*` directories (DL-043). In a project set up by `npx skills`, it would write the Claude Code variant through the `.claude/skills/dld-*` symlinks. That overwrites the portable copies in `.agents/skills/`, and every later update rewrites the same files twice. DL-043's symlink check covers only the skills directory and its parents, not each skill directory.
- The installer behaviour above is third-party and can change.

## Decision

- **dld-common stays installable by default.** The portable dld-common SKILL.md never carries `metadata.internal`, and a generator test asserts it.
- **Partial installs.** A partial install without dld-common is handled by the `{{dld-setup}}` check (DL-036), which names `npx skills add jimutt/dld-kit --skill dld-common`.
- **`dld init` and `dld update` never write through a symlinked skill directory.** If a `dld-*` entry in a target skills directory is a symlink, they fail before writing anything. The error names the entry, says another installer such as `npx skills` manages it, and says to update with `npx skills update` or remove those skills first. `--force` does not override this. It amends DL-043's symlink rule to cover each skill directory.
- **A warning when `npx skills` manages the skills.** When `skills-lock.json` at the project root lists a `dld-*` skill, `init` and `update` warn that `npx skills` manages those skills, and that `dld update` and `npx skills update` will overwrite each other's copies.
- **A CI job checks the installers.** It runs a script under `scripts/` that uses a pinned `npx skills@1.7.0` with the checked-out repository as a local source, in temporary projects:
  - **Full install.** `add <repo> --all -y`, with a `.claude/` directory present, installs every `dld-*` skill exactly once.
    - The installed text is the portable variant: no `${CLAUDE_SKILL_DIR}`, and nothing from `claude-plugin/` or `.claude/skills/`.
    - `.claude/skills/dld-*` are symlinks.
    - `node <skill>/../dld-common/scripts/dld.mjs --version` prints the package version through both the `.agents/skills` path and the `.claude/skills` path.
  - **Partial install.** `add <repo> --skill dld-plan -y` installs dld-plan without dld-common.
  - **Update after npx skills.** `dld update --agent claude`, run with the built CLI in the project from the full install, fails with the symlink error.
- **`gh skill` is checked by hand at release**, since it needs an authenticated `gh` and a release tag.

## Rationale

- `npx skills` is the most used skill installer, and its defaults (no dependencies, internal skills hidden, symlinked copies) meet dld-kit's shared dld-common directly.
- Refusing is safer than guessing which installer owns a symlinked skill.
- The CI check turns a change in the third-party installer into a failed build rather than a user report.

## Consequences

- The CI job needs network access to fetch the pinned `skills` package.
- Bumping the pinned `skills` version is a deliberate change.
- Whether Antigravity and Cursor tell the agent a skill's directory is still unverified. The portable text asks the agent for it either way (DL-036).
