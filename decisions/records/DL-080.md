## Context

IDs are global across namespaces (decision record format spec), but nothing enforces it. `create-decision --id DL-001` succeeds with no namespace, with each configured namespace, and with a namespace that is not in the config, which it creates as a new directory. INDEX.md then lists all the copies, and commands that find a record by ID, such as `update-status DL-001`, silently pick one of them. In a flat project `--namespace` is ignored without a word.

## Decision

- `create-decision` fails if a record with that ID already exists anywhere under the records directory, in any namespace or at its root. The error names the existing file.
- In a namespaced project, `--namespace` must be one of the configured `namespaces`. An unknown name is a usage error that lists them. Without `--namespace`, the record goes at the root of the records directory, as now.
- In a flat project, `--namespace` is a usage error.
- Commands that find a record by ID fail when the ID is in more than one file, listing the files, instead of picking one. That covers `update-status`, `rename-decision`, `related-decisions` (DL-077), and `check-decision-edits` and `restore-decision-prose` with IDs.
- `regenerate-index` prints a warning on stderr for every duplicated ID it finds.

## Rationale

- A global ID is what makes `@decision(DL-NNN)` unambiguous. Two records with one ID break every link to it.
- Rejecting unknown namespaces stops a typo from quietly creating a new namespace that no config, skill or PRACTICES.md knows about.

## Consequences

- Projects that already have duplicated IDs get errors from commands that target them, and warnings from `regenerate-index`, until `/dld-reindex` or a manual rename resolves them.
