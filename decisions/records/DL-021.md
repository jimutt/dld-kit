## Context

DL-003 established the four-part completion transaction — claim, mechanical check, review, record — and DL-020 recorded that the OpenCode spike shipped without it. On OpenCode, item completion currently relies on the agent following the skill's instructions: the agent claims an item verifying, runs verify-item.sh itself, and marks the item accepted. The agent grades its own homework, which is exactly what DL-003 forbids.

The Pi extension enforces the transaction in loop.ts onTurnEnd: when an item is verifying with new evidence, the loop runs verify-item.sh, and on pass either nags for review (review enabled) or runs the accept transaction — set-item-status accepted, repin-item, append-event item-accepted — with failure at each step aborting the rest. On fail, attempts<2 sends the item back to implementing; attempts>=2 blocks it.

## Decision

Port the four-part completion transaction to the OpenCode server plugin, driven off session.execution.succeeded.

After the loop's dispatch check, if the run has an item in verifying status whose evidence changed since the last verification, the loop runs verify-item.sh and applies the transaction:

- **Pass + review enabled** — the item stays verifying; the loop sends one synthetic message per item telling the agent to run the review, then waits. The agent claims via the skill, which flips review to done (the skill's existing flow).
- **Pass + review disabled** — the transaction: set-item-status accepted, repin-item, append-event item-accepted. Each step is checked; a failed step aborts the rest and surfaces an error.
- **Fail, attempts < 2** — set-item-status back to implementing; the next dispatch re-delivers the item with the failure as context.
- **Fail, attempts >= 2** — block-item.sh with the verification output as the reason, and the run pauses with a surfaced message.

Evidence-change detection uses a per-session map of item index to evidence count, same as the Pi extension's verifiedAtEvidence. The map is in-memory; a server restart re-verifies once, which is harmless.

## Rationale

The transaction is the difference between a loop that works and a loop that's correct. The OpenCode port already proved the dispatch half; without the completion half, a run can accept broken work as long as the agent says it passed.

Driving off execution.succeeded rather than a turn-end event is the OpenCode equivalent of Pi's turn_end hook — OpenCode's event granularity is coarser, but the transaction is idempotent (evidence-count gating), so extra invocations are harmless.

Review-enabled handling differs from Pi by necessity: Pi's nag goes to the user via notify; OpenCode's goes to the agent via synthetic, because the agent runs the review subagent, not the user.

## Consequences

The loop enforces DL-003 on OpenCode. An item can no longer complete on the agent's say-so alone — the mechanical check runs in the plugin process, outside the agent's context.

The dispatch guard (DL-020) interacts: after a retry, the item returns to implementing, the dispatch key no longer matches, and the next event re-delivers it — the retry flow works without extra wiring.

maxMinutes enforcement remains unported; it is a separate, smaller follow-up.
