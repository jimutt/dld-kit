## Context

The `/dld-goal` skill executes a long-running goal across many turns and sessions. It needs durable state: which decisions are in scope, which are done, what evidence was collected, and what happened when. That state must survive context compaction, session restarts, and crashes, because the whole point is that the agent cannot hold it in conversation.

Surveyed Pi goal-loop extensions split three ways on this: session-entry persistence only (lost with the session), a single mutable JSON document (torn writes, no history), or an append-only ledger plus an atomic snapshot. See `docs/plan/goal-loop.md` for the full survey.

DLD already has `.dld-state.yaml` for audit/snapshot run tracking, parsed with grep and sed. Extending that idiom to nested per-item acceptance criteria and evidence arrays would mean hand-rolling structured parsing in bash.

## Decision

Run state lives in `.dld/runs/<goal-slug>/`, gitignored by default:

- `contract.md` — human-readable objective, scope, and bounds, authored once at run start and treated as immutable by the loop.
- `state.json` — machine-readable items, statuses, and pointers. camelCase keys. Written atomically (temp file plus `mv`).
- `events.jsonl` — append-only timestamped event log.

The `dld-goal` scripts require `jq`, declared in the skill `compatibility` frontmatter. This is the first dependency beyond bash and git in the core path; it is scoped to this skill, and skills that do not touch run state stay dependency-free.

`/dld-goal start` adds `.dld/` to `.gitignore` on first run. A project can opt out via `dld.config.yaml` if it wants run history committed.

## Rationale

Decision records are the persistent artifact; run state is local working state. A run is one developer driving one goal on one branch — committing its event log would add noise to review without adding information that the decision log does not already carry. The decisions that came out of a run are permanent; the fact that item three needed two attempts is not.

JSON with `jq` over YAML with grep because the item schema is genuinely nested. Hand-parsing nested structures in bash is where correctness bugs live, and this state drives status transitions that must not silently corrupt. `jq` is ubiquitous, already used by `dld-reindex`, and the Stage 2 TypeScript extension reads the same files natively.

Append-only events plus an atomic snapshot means a crash mid-write cannot destroy history, and state can be reconstructed by replaying events if the snapshot is damaged.

## Consequences

Run history is not shared across a team by default, so a colleague cannot inspect why a run stalled unless the developer opts in or reports it.

`jq` becomes a hard requirement for `/dld-goal`. Environments without it get a clear precondition failure rather than degraded behaviour.

Runs are branch-local in practice. Switching branches mid-run leaves state pointing at decisions that may not exist on the new branch — handled by the precondition and hash checks in the related decisions.
