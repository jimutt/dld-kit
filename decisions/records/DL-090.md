## Context

DL-071 resolves the base branch from `base_branch`, a differently named upstream, `origin/HEAD`, then `origin/main` and `main`. A repository whose main branch is `master` and that has no remote, or no `origin/HEAD`, finds none of them. An end-to-end run of `/dld-plan` and `/dld-implement` in such a repository showed what that costs: `check-decision-edits` cannot protect anything, and `list-proposed` (DL-076) exits 1 without printing a single decision, so `/dld-implement`'s fallback of showing every proposed decision has nothing to show. Many existing repositories still use `master`.

## Decision

- After `origin/main` and `main`, the resolution tries `origin/master`, then the local `master`. The failure message lists every ref it tried, as before.
- `list-proposed` without `--base`, when no base resolves, prints every proposed decision with `unknown` in place of `branch` or `base`, and warns on stderr (through `Context.warn`) that no base branch was found and how to set one. It exits 0. An explicit `--base` that does not resolve still fails.
- `/dld-implement` treats `unknown` lines as it treats the list when the command could not find the base: it shows every proposed decision and asks which to implement, with none selected by default.
- The configuration spec's description of the resolution order adds `origin/master` and `master`.

## Rationale

- `master` is the other common default branch name; trying it last changes nothing for repositories that have `main`.
- Listing the decisions without their location keeps `/dld-implement` usable when the base is unknown, which is what its fallback always intended.

## Consequences

- Amends DL-071 (the resolution order) and DL-076 (`list-proposed` without a base).
- A repository with both `main` and `master` keeps resolving to `main`.
