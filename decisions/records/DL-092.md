## Context

Decision IDs are `DL-` plus a number, one above the highest in the log (DL-078). Two branches that each record a decision from the same base pick the same number. `/dld-reindex` repairs that afterwards, but the more people and agents work in a repository at once, the more often it is needed. `docs/plan/timestamp-ids.md` compares the alternatives (readable timestamp, ULID, UUIDv7, content hash, per-author ranges).

## Decision

- There is a second ID form, the timestamp ID: `DL-T` followed by 12 characters of Crockford base32 in lower case (`0123456789abcdefghjkmnpqrstvwxyz`), for example `DL-T1k3m9z2p7xq4`.
  - Characters 1 to 7 are the creation time in whole Unix seconds, most significant first, fixed width.
  - Characters 8 to 12 are 25 random bits.
  - As a pattern: `DL-T[0-9a-hjkmnp-tv-z]{12}`.
- This spelling is the ID's identity everywhere, as DL-078 says for sequential IDs: file name (`<id>.md`), frontmatter, annotations and references.
- It is the only canonical spelling. Upper-case letters after the `T`, a lower-case `t`, the letters `i`, `l`, `o` and `u`, and any other length are not canonical. Tools that create or rename IDs reject them (usage error, exit 2). When the rejected text becomes a valid timestamp ID by lower-casing it and reading `i` and `l` as `1` and `o` as `0`, the error names that spelling.
- Both forms are valid in every log, whatever the project is configured to create (DL-095). Commands that take or read an ID accept either.
- Commands that read existing IDs keep accepting what they find, as DL-078 decided.
- The record format spec describes both forms.

## Rationale

- The time part makes IDs sort by creation time as plain text, and makes two IDs collide only when they are created in the same second with the same 25 random bits: 1 in 33 million for a pair created in the same second. Inside one working copy `create-decision` refuses an existing ID, and across branches `find-collisions` still reports a collision.
- The ID appears in every annotation and in prose, so it should be short. A ULID is 26 characters and a UUID 36; this is 13 after `DL-`. The date does not need to be readable in the ID: every record has a `timestamp`.
- Crockford base32 has no `i`, `l`, `o` or `u`, so characters are hard to confuse. One spelling keeps text comparison exact, which is what annotations and references rely on.
- The `T` is required. The time part starts with a digit until the year 2310, and every pattern in 1.0 matches `DL-` plus digits. Without the marker a 1.0 CLI would read the leading digits of a timestamp ID as a decision number. With it, 1.0 does not recognise the ID at all.
- Seven base32 characters hold Unix seconds until the year 3059.

## Consequences

- A 1.0 CLI does not see timestamp records: its `regenerate-index` leaves them out and its scans skip their annotations. DL-098 adds a guard for later versions; for 1.0 the release notes say to upgrade every collaborator before switching.
- A timestamp ID is not something people say aloud or remember, unlike `DL-047`. That is the cost of not coordinating.
- The time in an ID can run a little ahead of the clock (DL-095), so it is an ordering key, not a record of when the decision was made.
