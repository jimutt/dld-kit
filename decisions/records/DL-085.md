## Context

DL-056 and DL-073 define the semver contract as five CLI commands (`init`, `update`, `install-rule`, `session-context`, `check-decision-edits`) plus `--help` and `--version`. `docs/releasing.md` says the same. Projects depend on more than those commands: their decision records, annotations and `dld.config.yaml` follow formats dld-kit defines, CI relies on the `Decision-Edit` trailer, users type the skill names, and installs go through the npm package, the plugins and the `skills/` layout. None of that is stated as covered, so a user cannot tell what 1.x promises them, and a maintainer cannot tell which change needs a major version.

Projects already add their own frontmatter fields: vaskaren's records carry `intents:` for an add-on that is still being tried out. Every command keeps fields it does not know, but the spec does not say so.

## Decision

From 1.0.0, a breaking change to any of these needs a major version:

- **Decision records:** their place (`records/` under the decisions directory, one subdirectory per namespace in namespaced projects), file names (`DL-<number>.md`), the ID syntax (DL-078), the frontmatter fields (`id`, `title`, `timestamp`, `status`, `supersedes`, `amends`, `namespace`, `tags`, `references` with `path` and `symbol`) and their meaning, the statuses and their lifecycle, and the body's section headings (Context, Decision, Rationale, Consequences), which the skills and the CLI read.
- **Projects' own fields and keys:** unknown frontmatter fields are kept by every command and by the skills when they edit frontmatter, and are otherwise left alone, except that renames rewrite decision IDs anywhere in a record. dld-kit never adds a frontmatter field or config key starting with `x-`, and config keys with that prefix never warn, so projects and add-ons can use it. Any other new field or key comes in a minor release, optional, and its changeset names it.
- **Annotations:** the syntax DL-074 specifies, and `annotation_prefix`.
- **`dld.config.yaml` and `dld.local.yaml`:** at the repository root, with their keys, their values and their defaults, the keys `dld.local.yaml` accepts and its precedence (DL-087). A minor release may add keys; an unknown key is a warning, never an error, throughout 1.x (DL-079).
- **The setup and CI commands** (DL-056, DL-073), including the `--agent` names, and the `Decision-Edit` commit trailer.
- **The installed layout:** where `init` and `update` put the skills and the always-on rule for each agent, and the `dld-kit:start` and `dld-kit:end` markers around the rule block. A 1.x `update` upgrades any install an earlier 1.x made.
- **Skills:** the names of the twelve user-facing skills and the arguments their documentation gives (such as `--full` for `/dld-snapshot`, or `tag:<tag>` for `/dld-implement`), and the name of the shared `dld-common` skill they need beside them. Removing or renaming a skill, or dropping a documented argument, is breaking.
- **Distribution:** the repository `jimutt/dld-kit` that marketplaces and installers name; the npm package `dld-kit` and its `dld` bin; the Claude Code plugin `dld` and its marketplace `dld-kit`; the Codex and Copilot CLI plugin and marketplaces; the Pi package; and the `skills/` directory layout that `npx skills`, `gh skill` and manual copies read.
- **File names in the decisions directory:** those dld-kit writes (`INDEX.md`, the snapshot documents, the files named in `snapshot_artifacts`, `.dld-state.yaml`) and those the skills read (`PRACTICES.md`, at the top and in each namespace).
- **Supported Node.js versions,** under the policy in DL-086.

Internal, and free to change in a minor release:

- the wording and steps of the skills, and the text of the always-on rule;
- the commands the skills run (DL-056), as long as the skill templates change with them;
- the layout of `.dld-state.yaml`;
- the content and format of generated documents (`INDEX.md`, the snapshot documents);
- the library API (DL-002) and the bundled CLI's location inside the skills.

The contract is stated in `docs/releasing.md`, and the README's CLI section points to it. The decision record format spec and the configuration spec state the rules for projects' own fields and keys.

## Rationale

- What users depend on is mostly formats and names, not commands. Stating them is what lets a user upgrade within 1.x without reading every changelog.
- Keeping the skill wording, the rule text and generated documents internal leaves room to improve how the skills work, which is where most changes happen.
- Saying that unknown frontmatter fields are kept turns existing behaviour into a promise, so add-ons can land in 1.x without a major version.

## Consequences

- Amends DL-056: the contract covers more than the CLI's setup and CI commands.
- Changing a frontmatter field's meaning, a config key, a skill name or the install layout needs a major version from 1.0.0. Adding a field, a key or a skill does not.
- A changeset that touches anything listed above is checked against this list when it is written.
