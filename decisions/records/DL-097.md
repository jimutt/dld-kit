## Context

`.dld-state.yaml` stores `decisions_included` as a number. `detect-snapshot-changes` reports records numbered above it as new, and records at or below it that changed in `<commit>..HEAD` as modified (DL-025, DL-070). A record merged late with an ID below the watermark is reported as modified, so it is not lost, as long as the stored commit resolves. Two gaps exist today and get more common with timestamp IDs (DL-092), which merge out of order all the time:

- When the stored commit does not resolve, only the watermark is used and late merges are missed.
- Only committed changes are compared, so a record edited or added but not yet committed is not reported as modified.

## Decision

- `update-snapshot-state` writes `decisions_included` as the full ID of the highest accepted or proposed record in the DL-093 order, for example `DL-091` or `DL-T1k3m9z2p7xq4`. Its confirmation line shows that ID.
- `detect-snapshot-changes` reads `decisions_included` as an ID, or as a bare whole number written by 1.0, which means the sequential ID with that number. Anything else is `mode: full`, as now.
- New decisions are the accepted and proposed records above the watermark in the DL-093 order. The `includes_proposed` rule of DL-070 is unchanged.
- Modified decisions are the records at or below the watermark that differ between the baseline commit and the working tree: committed changes, uncommitted changes and untracked record files.
- When the baseline commit cannot be resolved (missing, `unknown` with no usable `last_run`, or not a commit in this repository), the result is `mode: full`.
- Output lines and their format are unchanged. IDs are printed as they are, in the DL-093 order.

## Rationale

- The watermark still does its job once it compares IDs instead of numbers, so the smaller change is enough. Detecting everything from git alone would lose the cheap "new" list when the commit is unknown.
- `/dld-snapshot` reads records from the working tree, so change detection should look at the working tree too. `find-missing-amends` already does this for the audit.
- Without a baseline the modified list cannot be trusted, and an incremental run on a wrong list leaves the overview silently stale. A full run costs more but is always right.

## Consequences

- A state file written by 1.1 has an ID where 1.0 expects a number, so a 1.0 CLI treats it as `mode: full`. That is safe.
- Records changed but not committed when the snapshot ran are reported as modified again next time, once, which regenerates text that is already current.
- Projects whose stored commit has disappeared (a rebased or shallow history) get a full regeneration instead of an incremental one.
