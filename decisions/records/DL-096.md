## Context

"Already exists" is decided by number (DL-080), and `plan-renames` gives each collision the next number above the highest one taken (DL-027). Timestamp IDs (DL-092) have no number. Collisions between them are extremely unlikely but possible, and a project that switches form still has open branches with sequential IDs that collide the old way.

## Decision

- **Uniqueness.**
  - For sequential IDs nothing changes: two record files with the same number are duplicates, so a hand-made `DL-07.md` still blocks creating `DL-007`.
  - For timestamp IDs, two record files are duplicates when their IDs are the same text.
  - `create-decision`, the one lookup by ID and the `regenerate-index` warning of DL-080 follow these rules.
- **Reindex.** `find-collisions`, `list-taken-ids` and the open-PR scan work on both forms with the same logic.
- **`plan-renames`** gives each collision a new ID in the project's configured `id_format` (DL-095), whatever form the colliding ID has.
  - `sequential`: consecutive numbers above the highest sequential number taken or added locally, as DL-027 decided.
  - `timestamp`: IDs generated by the rule of DL-095 over the IDs taken or added locally, in plan order, each later than the one before up to that rule's 60-second limit, and none of them taken, added locally or already in the plan.
- `rename-decision` and `commit-reindex` accept plans that mix forms. A rename may change an ID's form.

## Rationale

- Keeping the number rule for sequential IDs keeps DL-080's protection against hand-made spellings. Timestamp IDs have one spelling (DL-092), so text equality is the whole rule.
- Minting replacements in the configured form means a project that has switched moves its remaining sequential collisions onto timestamp IDs, where they cannot collide again.
- The reindex machinery stays as the safety net for the rare timestamp collision instead of being switched off.

## Consequences

- In a timestamp project `/dld-reindex` normally finds nothing, apart from branches opened before the switch.
- A rename from a sequential ID to a timestamp ID rewrites `DL-005s` to the new ID followed by `s`, which no scan reads as an ID. Sequential IDs end where their digits end (DL-094), and leaving the old text in place would be just as wrong. Such text is rare; `find-stale-mentions` and review are the check.
- A plan in a timestamp project is not reproducible: running `plan-renames` twice gives different new IDs. The skill already passes one plan through to the commands that apply it.
