## Context

`1.0.0-rc.1` and `1.0.0-rc.2` are published from tags on `v1`. Testing them in other repositories found real bugs: the rule placement report (DL-054) and annotation false positives from installed skills (DL-060). The project owner wants another release candidate after this workstream rather than 1.0.0, and no hurry to 1.0.

`v1` merges into `main` for 1.0 (docs/plan/v1.md), through draft PR #76. The Claude Code, Codex and Copilot CLI marketplaces read the default branch, `main`, which still holds the pre-1.0 skills. Until the merge, testers install the plugin with `jimutt/dld-kit#v1`.

## Decision

- **This workstream ends with `1.0.0-rc.3`,** tagged on `v1` with `npm version 1.0.0-rc.3` after its PRs merge. It publishes to the `next` dist-tag (DL-052).
- **The release candidates continue from `v1`,** as rc.4 and so on, until the project owner judges them clean in real repositories. There is no fixed number of candidates and no date.
- **The steps for 1.0.0, when that time comes:**
  1. Merge `v1` into `main` (PR #76), so the marketplaces serve the 1.0 plugin.
  2. Run `npm version 1.0.0` on `main` and push the tag.
  3. Remove the README's "Early development" note in that release.
  4. Retire `v1`: stop CI triggering on it, and state in `docs/releasing.md` that `main` is the release branch.
  5. Mark docs/plan/v1.md as done.

  None of these happen in this workstream.
- **Docs now.** `docs/releasing.md` says that release candidates come from `v1` until 1.0.0, and lists the 1.0.0 steps above.

## Rationale

- Each candidate so far surfaced bugs that tests missed. More real-world runs before committing to the 1.0 contract (DL-056) cost little.
- Merging to `main` only for 1.0.0 keeps the default-branch marketplaces on a known state until then.

## Consequences

- Marketplace users on the default branch keep getting the pre-1.0 skills until 1.0.0. Testers use the `#v1` ref.
- Amends DL-052 (the release branch before 1.0.0).
