## Context

The OpenCode spike needs to validate the riskiest unknowns before investing in the full implementation. The unknowns are: can a server plugin and CLI plugin share state, does `session.prompt` from a plugin drive a turn, and does `Bun.$` behave as an exec shim.

## Decision

The spike validated four of five targets:

1. **State sharing** — resolved: the CLI plugin reads `.dld/runs/` from disk. `ctx.storage` is server-only. Local-only for v1.
2. **Loop dispatch** — validated: `session.execution.succeeded` fires, `ctx.session.prompt` drives a turn, the loop dispatched item 1 and the agent worked it. The event fires with two shapes (one with `data.sessionID`, one without); filtering on `data?.sessionID` handles it.
3. **Exec shim** — validated: `execSync` with try/catch replaces `pi.exec`, preserving exit codes and stderr. `Bun.$` was not needed.
4. **Status line** — implemented in `tui.tsx` but not yet tested interactively (requires a TUI session).
5. **Widget** — implemented in `tui.tsx` but not yet tested interactively.

The workspace root comes from `session.location.directory`, not `process.cwd()` — the plugin runs in OpenCode's server process with a different cwd than the project. This was the spike's main discovery.

Original plan:

1. **State sharing** — server plugin writes run state to `ctx.storage`; CLI plugin reads it. If `ctx.storage` doesn't bridge, fall back to both processes reading `.dld/runs/` from disk.
2. **Loop dispatch** — server plugin subscribes to `session.idle`, reads the active run, dispatches `ctx.session.prompt` with `delivery: "queue"`.
3. **Exec shim** — `Bun.$` with `.nothrow()` replaces `pi.exec`, preserving exit codes and stderr.
4. **Status line** — CLI plugin renders `statusLine()` into `prompt.footer.status` slot.
5. **Widget** — CLI plugin renders `widgetLines()` into `session.composer.top` or `sidebar.content` slot.

The spike does not include: board overlay, per-session state maps, Esc detection, or findings log. Those come after the loop is proven.

## Rationale

State sharing is the highest risk because it's undocumented. If `ctx.storage` is server-only, the CLI plugin can't read it, and the fallback (disk) only works locally. The spike must answer this before anything else matters.

Loop dispatch is the core mechanism. If `session.prompt` doesn't drive a turn from a plugin, the whole approach fails.

Exec, status, and widget are lower risk — they're adapting known patterns to a new API.

## Consequences

The spike produces a minimal working plugin or a clear no-go. If state sharing fails and disk fallback is acceptable, the plugin is local-only for v1. If loop dispatch fails, the approach needs rethinking.
