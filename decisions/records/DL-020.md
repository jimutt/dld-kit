## Context

The first live test of the OpenCode plugin surfaced a dispatch-spam failure: a session resuming a run with an in-flight item re-dispatched the identical continuation prompt on every execution completion, filling the transcript. An Opus 5 review of the spike found the root causes and a set of related defects.

## Decision

Fix the loop gating and error mapping per the review's critical findings:

1. **Dispatch guard**: the loop tracks which item each session was last told to work (`lastDispatch` map) and skips re-dispatching it. A turn ending mid-item (question, rate limit, context boundary) no longer triggers an identical prompt. The guard clears on session change, resume, pause, or dispatch failure.
2. **Error mapping mirrors the Pi extension**: next-item exit 2 → pause with a surfaced message; other non-zero → skip silently (script failure, never "complete"); exit 0 with empty stdout only → complete.
3. **Paused runs are resumable**: slug resolution falls back to `run-state.sh list` filtered on paused/blocked, and resume re-runs guard-preconditions (DL-004).
4. **execFileSync, not execSync**: argv arrays, no shell. Quoting bugs and injection through slugs/titles are gone, as are paths with spaces.
5. **TUI reactivity**: signal reads live inside JSX expressions, not component bodies — Solid untracks component bodies, which is why the sidebar went stale despite the watcher.
6. **Pause interrupts the in-flight turn** (ctx.session.interrupt), stop writes "stopped" not "complete", state transitions append to the event log, partial start blocks the run instead of going live half-populated.

## Rationale

The dispatch guard replaces the Pi extension's token mechanism with a simpler per-session memory. The Pi token voids in-flight dispatches when the loop state changes; the OpenCode guard prevents the dispatch from being issued at all. Both answer "don't deliver work the session already has," but the OpenCode version also covers the session-restart case the token doesn't.

The reactivity fix is a SolidJS semantic, not a design choice: component bodies run untracked, so any signal read assigned to a const is invisible to the reactive graph. The read must appear in the JSX expression itself.

## Consequences

The loop is quieter and safer. Blocked items and completions surface as synthetic messages with the relay phrasing. The run state machine matches the Pi extension's semantics.

Still unported and recorded as future work: the four-part completion transaction (verify → accept → repin → append-event) and maxMinutes enforcement. Item completion on OpenCode currently relies on the agent following the skill, which DL-003 forbids in principle — a follow-up decision must either port the transaction or explicitly accept the gap.
