## Context

DL-045 installs the rule once per harness. DL-054 recorded when Claude Code reads the managed block in AGENTS.md: only when there is no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md`. When dld-kit relies on that, it prints a note, because any of those files added later (including one developer's uncommitted `CLAUDE.local.md`) silently stops Claude Code from reading the block.

Claude Code's memory documentation (September 2026):

- **All three CLAUDE files load.** Claude Code loads every one of `CLAUDE.md`, `.claude/CLAUDE.md` and `CLAUDE.local.md` that exists. It reads AGENTS.md directly only when none of them exists.
- **Imports.** A `@path` import in a CLAUDE file loads that file. Relative paths resolve from the importing file.
- **No double reading.** Keeping an `@AGENTS.md` import "never makes Claude read AGENTS.md twice", whichever mode is set.
- **Older versions.** Importing AGENTS.md from a CLAUDE file is the documented way to give Claude Code the file where it cannot read it directly, including versions before v2.1.277.
- **No project setting.** The setting that makes Claude Code read both kinds of file is ignored in project settings files, so a repository cannot opt in for its developers.

A second problem follows from the same rules. A project whose `CLAUDE.md` already imports `@AGENTS.md`, a common setup, gets the block in AGENTS.md. dld-kit checks only whether CLAUDE.md itself holds the block, so it also writes `.claude/rules/dld-workflow.md`, and Claude Code loads the rule twice.

## Decision

- **What Claude Code reads.** dld-kit models it as follows:
  - Every CLAUDE file that exists at the project root (`CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`).
  - Plus AGENTS.md when one of them has a line that imports it (`@AGENTS.md`, or `@../AGENTS.md` from `.claude/CLAUDE.md`, outside code spans and fences).
  - When none of the three exists, Claude Code reads AGENTS.md directly.

  Claude Code loads the rule when any file it reads holds the block. `planRule` and `loadsRule` (so also `session-context`) use this model instead of the first-existing-file rule for Claude Code.
- **The import file.**
  - When the plan leaves Claude Code reading the block only by reading AGENTS.md directly, dld-kit creates `.claude/CLAUDE.md` instead of relying on that. This holds when the `claude-file` channel is installed, the block is in AGENTS.md, and none of the three CLAUDE files exists.
  - The file holds the generated-file notice (DL-044) and one line, `@../AGENTS.md`.
  - Claude Code then reads AGENTS.md through the import. The rule loads once, and it keeps loading when a `CLAUDE.md` or `CLAUDE.local.md` appears later.
- **Ownership.**
  - dld-kit creates `.claude/CLAUDE.md` only when it does not exist, and rewrites it only when it carries dld-kit's notice.
  - It never removes it: a leftover import is harmless, per the documentation.
  - A `.claude/CLAUDE.md` without the notice belongs to the user and is only read.
- **Output.** `init`, `update` and `install-rule` report "Wrote .claude/CLAUDE.md (imports AGENTS.md for Claude Code)". DL-054's note is removed.
- **Existing projects.** `dld update` creates the file in projects set up by rc.1 and rc.2 that rely on AGENTS.md.

## Rationale

- The import is Claude Code's own recommended bridge. It keeps the rule to one copy and closes the gap DL-054 could only warn about.
- `.claude/CLAUDE.md` rather than a root `CLAUDE.md` keeps dld-kit's file inside `.claude/`, out of the root instruction files the user edits, and out of Pi's and OpenCode's CLAUDE.md fallback.
- Following imports fixes the duplicate rule for projects that already import AGENTS.md.

## Consequences

- dld-kit creates one more file in the user's `.claude/` in the AGENTS.md-only case.
- Claude Code loads the whole AGENTS.md through the import, as it already did when reading AGENTS.md directly. After a CLAUDE.md is added, it keeps loading AGENTS.md alongside it, which is the purpose.
- Amends DL-045 (how Claude Code gets the block) and DL-054 (its note and Claude Code's instruction list).
