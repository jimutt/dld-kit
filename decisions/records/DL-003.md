## Context

The loop needs to decide when an item is done. Every Pi goal-loop extension surveyed answers this differently, and the spectrum is instructive: the weakest let the model declare completion with a marker string or a tool call, the strongest run an independent auditor in a fresh process that never saw the implementing conversation. The failure mode the strong designs are defending against is the agent that did the work grading its own homework and passing.

DLD is unusually well placed here. It already has mechanical completion signals that generic loops lack: `verify-annotations.sh` proves the code actually carries the annotations the decision claims, project test commands prove behaviour, and `/dld-implement` already runs a review subagent over the diff with fresh context.

## Decision

An item completes only when four steps pass, in order:

1. **Claim** — the implementing agent reports done through the normal `/dld-implement` flow.
2. **Mechanical check** — `verify-annotations.sh` passes for every decision in the item, and the item acceptance commands run and exit 0. Output is captured as evidence.
3. **Review** — the `implement_review` subagent approves the diff. Critical findings block; the existing judgment rules for moderate and minor findings apply.
4. **Record** — statuses flip to `accepted` via `update-status.sh`, and an event with the collected evidence is appended.

A claim alone never closes an item. If step 2 or 3 fails, the item does not complete and the blocked-item policy takes over.

Acceptance commands default to the project test suite plus annotation verification. Per-item commands can be declared during contract authoring where the default is too broad or too weak.

Acceptance commands are stored as argv arrays and executed directly, never through a shell. Commands needing operators, quoting, or substitution must live in a repo script that the contract invokes.

## Rationale

This composes machinery DLD already trusts rather than introducing a new verifier. It costs no new dependency and no new failure surface, and it inherits improvements to the review step automatically.

Ordering matters: mechanical checks run before the review because they are cheap, deterministic, and catch the common failures. Paying for an LLM review of code that does not compile is waste.

A detached auditor process — the strongest option in the survey — was deliberately not chosen for this stage. It is the single largest source of operational complexity in the extensions that have it, and the in-session review with mechanical gating is the right strength until false approvals are shown to be a real problem here.

## Consequences

Completion is only as strong as the declared acceptance commands. A project with a weak test suite gets a weak gate; the annotation check still holds, but behavioural correctness rests on what the project can actually verify.

The review subagent runs per item, so a run with many items costs many reviews. This is deliberate — it is the same cost `/dld-implement` already pays, just repeated.

Runs cannot complete in projects that disable `implement_review` unless the skill treats that setting as an explicit opt-out of step 3. It does, and records the weaker gate in the run events.

Checks cannot express compound commands. A project wanting `test && lint` writes a script and points the contract at it. This costs a file, and buys a check pipeline that lives in version control where it can be reviewed and diffed, rather than in per-run state that executes later in a context nobody re-reads.
