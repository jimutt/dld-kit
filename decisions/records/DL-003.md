## Context

The CLI ships in two forms: as the npm package's command, and as a single zero-dependency file (`dld.mjs`) bundled inside the skills, so marketplace and `npx skills` installs work without an npm install (docs/plan/v1.md). The code also needs a strict typecheck, and declaration output if the library is ever consumed.

## Decision

- `tsc` is used for typechecking (`tsc --noEmit` in CI) and, when needed, emitting `.d.ts` declarations. It does not produce the runtime JavaScript.
- esbuild bundles the CLI entry point into one ESM file, `dld.mjs`, targeting `node20`, with all dependencies inlined and Node built-ins left external. The output starts with a `#!/usr/bin/env node` shebang.
- That same bundle is both the npm `bin` target and the file copied into the skills. There is one build artifact, not two.
- The build is a single script (`npm run build`), runnable under Node.

The build script is `scripts/build.mjs` (`npm run build`), entry point `src/bin.ts`, output `dist/dld.mjs` (gitignored).

## Rationale

- esbuild is mature, fast, a single dependency, and needs almost no configuration for a Node ESM single-file bundle.
- Separating type checking from bundling is the conventional, low-risk split: tsc is authoritative on types, esbuild is fast at emitting.
- Using one artifact for npm and the skills means the code users run is identical regardless of how they installed it.

## Consequences

- Runtime dependencies must be bundle-friendly (no native modules, no dynamic `require` of files at runtime).
- Bundle size is visible and should stay small; it is copied into every install.
- Alternatives considered: tsdown (newer, more opinionated) and `bun build` (would make Bun a build requirement for shipped output, against the runtime decision).
