## Context

1.0's primary distribution for the CLI is npm (docs/plan/v1.md). The package needs a name, a command name, and a clear boundary of what is public. The unscoped name `dld` is taken on npm; `dld-kit` is free and matches the repository and project name.

## Decision

Publish the unscoped npm package `dld-kit`. It installs one command, `dld` (`bin: { "dld": ... }`).

`package.json` declares `"type": "module"`, `"engines": { "node": ">=20" }`, and an explicit `files` allowlist so only built output, skills, and docs ship — never tests, sources of test fixtures, or development config.

For 1.0 the CLI (commands, flags, exit codes, output formats consumed by skills) is the public contract and follows semver. The library is importable but its API is not committed until a later decision says so; it is documented as internal.

## Rationale

- `dld-kit` matches the repo, the existing Tessl and pi identities, and is available. A short command name (`dld`) matters more than a short package name, and bin names are independent of package names.
- An explicit `files` list is the only reliable way to keep the published tarball small and free of development leftovers.
- Committing only to the CLI keeps the port free to reshape internals; skills depend on the CLI, not on library imports.

## Consequences

- `npm i -g dld-kit` / `npx dld-kit` install and run it; the command is `dld`.
- The `dld` bin name could clash with another globally installed package providing `dld`; accepted as unlikely.
- A future decision is needed before external code may rely on the library API.
