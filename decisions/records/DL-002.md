## Context

A goal run executes a set of proposed decisions. The loop needs a unit of execution: the thing that gets implemented, verified, and marked done as a whole.

One decision per unit is the obvious choice and gives the sharpest verification signal. But `/dld-implement` already recognises that some decisions cannot sensibly be implemented alone — a data model, its validation, and its state machine share types and produce throwaway code if split across separate passes. Decision boundaries are drawn for rationale clarity during planning, not for implementation independence, so the split is sometimes impossible to avoid.

Separately, a run can outlive the decisions it targets. A developer can run `/dld-adjust` on a proposed decision, or pull a branch that changes one, while a run is paused. Continuing to implement against a stale snapshot of intent is the quiet failure mode.

## Decision

A work item contains one or more decisions. Batching follows the rule `/dld-implement` already applies: decisions batch when they touch the same code, share types, or depend on each other so heavily that implementing one without the others produces incomplete or throwaway code. Decisions that merely share a tag or namespace are not coupled and execute as separate items.

Each decision in an item is pinned by a content hash recorded at contract-authoring time:

```json
{
  "decisions": [
    { "id": "DL-014", "hash": "sha256:..." },
    { "id": "DL-015", "hash": "sha256:..." }
  ],
  "status": "pending"
}
```

Before an item runs, and before a paused run resumes, hashes are re-checked. A mismatch invalidates the item and any cached verification for it, and the run stops for the operator to replan rather than continuing.

The completion transaction applies to the item as a whole: all annotations verified, all acceptance checks green, one review pass over the combined diff, then each decision in the item flips to `accepted`.

## Rationale

Forcing one decision per item would make the loop unusable for exactly the plan groups it is meant to execute, since tightly coupled decisions are common output from `/dld-plan`. Allowing arbitrary batching would collapse the gate to a single pass over an entire feature. Reusing the existing coupling rule keeps one definition of "these belong together" across the manual and automated paths.

Hashing rather than timestamps because a decision can be edited and restored, or touched by a rebase without changing content. What matters is whether the intent the item was planned against still holds.

Stopping rather than auto-replanning on mismatch: the decision changed because a human changed it, so a human decides what that means for work already in flight.

## Consequences

A batched item cannot tell you which decision caused a failed check, and the review subagent sees a larger, colder diff. Batches must be kept small; this is guidance in the skill, not a mechanical limit, and whether a hard cap is needed is still open.

Adjusting a decision mid-run always costs an interruption, even when the edit was cosmetic. Accepted as the safe default.
