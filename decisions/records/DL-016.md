## Context

A long goal run works autonomously for potentially hours across many decisions. The run contract captures what happened mechanically — events, evidence, status changes — but not what the agent noticed along the way. When a single-decision `/dld-implement` finishes, the agent organically summarizes review findings, potential amendments, and notable observations. A goal run loses that entirely: the session compacts, the context window turns over, and the agent's on-the-fly observations vanish.

The makerday extension experimented with a working-log sidechannel for exactly this: the agent records unaddressed cases and decisions made on the fly, and the UI surfaces them. The concept was sound; the implementation was session-scoped and lost on compaction.

## Decision

Add a findings log to the run contract. A run's directory gains a fourth file:

```
.dld/runs/<slug>/
  contract.md      # what we agreed to do
  state.json       # where we are
  events.jsonl     # what happened mechanically
  findings.md      # what the agent noticed — appended, never rewritten
```

**Appending.** The agent appends findings during execution. Each entry is a short markdown note with the item index, the decision IDs it relates to, and the observation. The skill's instructions tell the agent to record a finding when it encounters something the plan didn't anticipate: an unhandled edge case, a decision made on the fly, code that contradicts an assumption, a risk noticed but not acted on. The extension registers a `dld_run_note` tool so the agent can append without shelling out.

**Surfacing.** On run completion, the extension reads the findings log and produces a summary notification plus a transcript card with the full content. The user sees what the agent noticed without reconstructing it from scrollback. During the run, the board overlay shows a findings section.

**Persistence.** `findings.md` is append-only and lives in the run directory, so it survives compaction, session restarts, and crashes. It is gitignored with the rest of `.dld/runs/` by default; `goal_run_artifacts: commit` includes it for teams that want the audit trail.

## Rationale

The run contract already separates three concerns: intent (contract.md), state (state.json), and execution (events.jsonl). Findings are a fourth concern — observation — and they deserve their own file because they serve a different audience: the human reviewing the run, not the agent executing it.

A markdown file rather than JSONL because findings are prose. The agent writes them as notes, not structured data, and the user reads them as a report. Markdown is the right format for both.

A tool rather than a bash script call because the agent should not need to know the run directory's path. The extension resolves it, appends, and confirms — the agent says "note this" and moves on.

Surfacing on completion rather than continuously because a finding is a review artifact, not a progress signal. The widget and status line already show progress; findings are what you read when the run is done.

## Consequences

The run contract gains a file. The skill's execution instructions grow by a section on when and how to record findings. The extension gains a tool, a card, and a board section.

Findings are advisory, not gating. A run can complete with findings unaddressed; they surface for the user to decide whether they warrant follow-up decisions. This is deliberate: a finding that blocks the run is a blocker, not a finding.

The agent decides what counts as a finding, which means the quality of the log depends on the prompt. The skill's instructions must be specific about what to record, or the log fills with noise.
