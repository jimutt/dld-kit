## Context

Without the extension, a run advances because the user types `/dld-goal continue`. The first job of the extension is to remove that keystroke: when the agent finishes a turn and the run still has work, the next item should start on its own.

Pi fires `agent_end` when a low-level run ends, and `agent_settled` when nothing further is queued. Extensions can inject a message with `sendMessage` or `sendUserMessage`, optionally triggering a turn. This is the mechanism every surveyed in-session loop uses.

The failure modes are well documented across those implementations: dispatching while the user is typing, dispatching twice for one turn, and stale callbacks firing after a pause or a session switch.

## Decision

The extension continues an active run from `agent_end`, subject to every one of these gates:

1. A run is active for this workspace, and its status is `active`.
2. The agent is idle and has no pending user messages (`ctx.isIdle()`, `ctx.hasPendingMessages()`).
3. The dispatch carries the current run token. A monotonic token is minted whenever the run starts or resumes; a queued continuation whose token no longer matches is discarded.
4. Bounds allow it: neither `maxItems` accepted nor `maxMinutes` elapsed. Exceeding either pauses the run and reports, rather than continuing.
5. `next-item.sh` selects an item. Exit code 2 (a blocked item) pauses and surfaces the operator question instead of continuing.

Continuation is delivered as a custom message with `deliverAs: "followUp"` and `triggerTurn: true`, instructing the agent to work the selected item exactly as the skill describes.

Any user input suspends continuation until the user resumes. Esc pauses the run.

## Rationale

Gating on idle plus no-pending-messages is the consensus safety pattern; a loop that dispatches over a user who is mid-sentence is worse than no loop.

The run token exists because pause, resume, stop, and session switching all create windows where a callback scheduled earlier is no longer valid. Comparing a token at dispatch time is cheaper and more reliable than trying to cancel every scheduled path.

Bounds are enforced at dispatch rather than trusted to the agent. The skill instructs the agent to check them, but instructions are advisory and this is the place where the check is mechanical.

`agent_end` rather than `agent_settled` because pi may still retry or auto-compact after `agent_end`; the idle and pending checks handle that, and `agent_end` gives a faster handoff between items.

## Consequences

Continuation shares one conversation, so context accumulates across items and pi compacts it. Acceptable for v1 and cheaper than session rotation; per-item context isolation is a separate decision.

A continuation triggers a turn the user did not type. The status line must make it obvious that a run is driving, or the session becomes confusing to watch.

Bounds pause rather than stop, so a paused run at a bound is resumable after the user raises the limit.
