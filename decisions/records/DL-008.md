## Context

PRACTICES.md asks for dependency injection over module-level side effects so failure branches are reachable from unit tests. The bash scripts shell out to `git` and touch the filesystem freely. The core library (DL-007) needs a single, predictable way to reach the outside world.

## Decision

Core functions receive a `Context` object:

- `cwd` — the directory the command runs from.
- `fs` — a narrow synchronous filesystem interface covering only what core uses (read, write, exists, list directory, mkdir, rename). The real implementation wraps `node:fs`.
- `git(args)` — runs `git` in `cwd` and returns stdout, throwing `DldError` on a non-zero exit. The real implementation uses `node:child_process` `execFileSync`.
- `env` — a read-only view of environment variables.

The interface grows only when a ported command needs a new operation. I/O is synchronous.

Tests use the real implementations against temporary git projects for the normal paths, and hand-written fakes (e.g. an fs whose `writeFile` throws) for failure branches. No mocking library.

## Rationale

- One object is easy to thread through calls and easy to fake. A narrow interface keeps fakes small.
- Synchronous I/O suits a short-lived CLI that does one thing and exits, keeps call sites simple, and matches the sequential bash scripts being ported.
- `execFileSync` with an argument array avoids shell quoting problems.

## Consequences

- Async would need an interface change if a future command benefits from concurrency (e.g. scanning a large tree). That is acceptable for 1.0.
- Code that reaches `node:fs` or `node:child_process` directly from core is a review finding.
