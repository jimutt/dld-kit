## Context

The docs say a decision's content is immutable once it is `accepted`. In practice this goes wrong in two directions:

- An agent refuses to change a record because it is `accepted`, even though the record only exists on a local or unmerged branch. `dld-implement` marks a decision `accepted` as soon as the code is written, so most records on a feature branch are `accepted` long before anyone else has seen them.
- In ordinary sessions, outside the skills, agents edit the prose of old, merged decisions, to "align them with today" or to add an amendment note. The always-on rule says nothing about editing records, so nothing stops this.

`dld-adjust` has its own test: a record is published once its last commit is on any remote branch. Pushing a feature branch to open its PR then counts as published, and no other skill uses the test.

## Decision

- A record's prose locks when it reaches the base branch, not when it is accepted. A record is **integrated** when its file exists at the merge-base of the base branch and HEAD; otherwise it is a **draft**, whatever its status. Drafts can be edited freely.
- A record that is still `proposed` in its merge-base copy is a draft too. Decisions PRs often merge `proposed` records that are implemented later, and proposed records have always been mutable.
- Frontmatter is always editable, at every strictness level: `status`, `references`, `amends`, `supersedes`, `tags`, `title` and the rest. Only the body (everything after the frontmatter) of an integrated record is protected; `decision_edits` decides how strictly.
- The base branch is the one `resolve-base` picks (the upstream when it tracks another branch, else `origin/main`). When that is a remote ref that doesn't exist, the local branch of the same name (`main`) is used, so local-only repositories work.
- New internal command `dld check-decision-edits [--base <ref>] [DL-NNN ...]`. Without IDs, it prints `<path>\t<DL-NNN>\tedited` for each integrated record whose body differs from its merge-base copy (in the working tree, committed or not), and `deleted` for each integrated record that is gone. With IDs, it prints one line per ID, with state `draft`, `integrated`, `edited` or `deleted`. It exits 1 when `decision_edits` is `block` and it printed an `edited` or `deleted` line; otherwise 0.
- Bodies are compared as text after the frontmatter, with CRLF read as LF.

## Rationale

- "Has the rest of the team got it" is what makes a record history. The base branch answers that; a status does not, and neither does a pushed feature branch.
- The merge-base, not the base's tip, is the right copy to compare against: if the base changed a record after the branch forked, the branch did not edit it.
- Frontmatter is bookkeeping: status changes, new links, moved references, retags. Locking it would force new decisions for mechanical changes, which is what the format already avoids for `status` and `references`.
- A git diff never misses an edit and never reports one that isn't there, so the check is exact; the agent's judgment goes into what to do about it, not into noticing it.

## Consequences

- Agents can rework `accepted` records freely until the branch is merged.
- Moving a record between namespace directories on a branch reports the old path as `deleted`.
- A record that reached the base under a different file (e.g. a reindex rename) is a draft at its new path.
