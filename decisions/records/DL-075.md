## Context

INDEX.md lists decisions newest first (DL-018), so every branch that adds a decision inserts rows at the top of the table. Any two pull requests that both add decisions conflict on INDEX.md, even when their IDs differ. The fix is to run `regenerate-index`, which GitHub's merge button cannot do, so teams resolve the conflict by hand on every parallel plan.

## Decision

- `init` and `update` make sure `.gitattributes` at the project root contains the line `/<decisions_dir>/INDEX.md merge=union`, preceded by the comment `# dld-kit: keep both sides' rows when merging the decision index`.
  - The file is created if it does not exist.
  - The line is added only when no line in the file already sets a merge attribute for that path. A user's own setting wins, and dld-kit never edits or removes other lines.
  - When `decisions_dir` changes, `update` adds the line for the new path. It leaves an old line in place, with a warning.
- The INDEX.md layout is unchanged: a fixed header, one self-contained line per row and no counts. That is what lets a union merge produce a valid table.
- The dld-init skill does the same through the CLI.

## Rationale

- With the union driver, git keeps the rows from both sides instead of reporting a conflict. That works in every merge, including GitHub's merge button, and needs no custom merge driver installed on anyone's machine.
- Leaving INDEX.md committed keeps it browsable on GitHub, which is what it is for.

## Consequences

- After a union merge the rows can be out of order, and a row both sides changed (for example a status) appears twice, until the next `regenerate-index`. Every skill that changes records already runs it.
- `.gitattributes` is the user's file, so dld-kit adds a line to it but treats everything else in it as theirs.
