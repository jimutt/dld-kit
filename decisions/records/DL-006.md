## Context

dld-kit ships as markdown and bash: skills for Tessl and Claude Code, plus shell scripts. Stage 2 adds a Pi extension (DL-005), which is TypeScript and needs a packaging and testing story the repo does not have.

Pi loads packages from npm, git, or a local path. A package declares resources through a `pi` manifest in `package.json`, or by convention directories (`extensions/`, `skills/`, `prompts/`, `themes/`). Pi loads TypeScript extensions directly — no build step is required.

## Decision

dld-kit itself becomes a Pi package. A root `package.json` declares:

```json
{
  "keywords": ["pi-package"],
  "pi": { "extensions": ["./extensions"], "skills": ["./skills"] }
}
```

The extension lives in `extensions/dld-goal/`, written in TypeScript and shipped as source. No bundler, no build output, no compile step before install.

Tests use `bun test` against a faked `ExtensionAPI`, colocated in `extensions/dld-goal/`. Bash scripts keep their bats suite; the two runners cover different layers and do not overlap.

Installation for development is `pi install /path/to/dld-kit`, which loads a local directory without copying.

## Rationale

One repository, one manifest, both halves in step. The skill and extension share the run contract, and a contract change that lands in one without the other is a bug; keeping them in a single package makes that impossible to ship accidentally.

No build step because Pi does not need one, and every build step is a way for published output to drift from source. It also keeps the repository honest: what you read is what runs.

`bun test` rather than the Node runner because it executes TypeScript directly with no loader configuration, and bun is already available. The faked-API approach is borrowed from ralphi, whose loop controller injects every collaborator as a function specifically so the loop can be tested without a live harness.

Declaring the manifest explicitly rather than relying on convention directories keeps `rules/` and `docs/` from being picked up as resources by a future convention change.

## Consequences

The repository gains npm packaging, `node_modules`, and a lockfile. Contained to the root manifest and `extensions/`; the skills and scripts stay dependency-light and keep working through Tessl and manual install untouched.

Two test runners now exist. Contributors need both bats and bun, and CI must run both.

Publishing to npm is possible but not required by this decision. Local-path install carries all of Stage 2 development.
