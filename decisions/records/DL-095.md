## Context

DL-092 defines the timestamp ID. Something has to decide which form a project creates, and how the time and random parts are produced. `/dld-plan` and `/dld-retrofit` create several records in a row, calling `next-id` before each one.

## Decision

- **Config.** `dld.config.yaml` gains `id_format`: `sequential` (the default) or `timestamp`. Any other value makes the config invalid. It only selects the form of new IDs; existing records are untouched and both forms stay valid (DL-092).
- **`next-id`** prints one ID in the configured form.
  - `sequential`: one more than the highest sequential number in the log, as DL-078 decided. Timestamp IDs in the log are ignored for this.
  - `timestamp`: the time part is the current time in whole seconds. If the newest timestamp ID among the local records is at or ahead of that, by no more than 60 seconds, the time part is that ID's time plus one second. The random part is 25 fresh random bits. If the result already exists locally, it is generated again.
- A local timestamp ID more than 60 seconds ahead of the clock is ignored when generating, and `/dld-audit` reports it.
- **`create-decision`** keeps `--id`, which accepts a canonical ID of either form whatever `id_format` says. It gains `--auto-id`, which creates the record under a new ID in the configured form and prints the path as now. Exactly one of the two is required.
- **Randomness is injected.** `Context` gains `randomBytes(n)`, backed by `node:crypto` in the real context, as DL-008 does for the clock and the filesystem.

## Rationale

- Sequential stays the default so that nothing changes for a project that does not opt in. A setting in the committed config makes the whole team create the same form.
- An agent's calls are normally more than a second apart, so IDs come out in creation order by themselves. The plus-one-second rule covers scripted or very fast creation, where several IDs would share a second and the random part would shuffle them.
- The 60-second bound matters. Without it, one record with a far-future time (a wrong clock) would make every later ID "newest plus one second". Concurrent branches would then share the time part and uniqueness would rest on the random bits alone.
- `--auto-id` closes the gap between `next-id` and `create-decision` when two agents share a working copy, and keeps `--id` for callers that want the ID before writing the body.

## Consequences

- During a burst the time in an ID runs ahead of the clock by up to a second per record, never more than 60 seconds in total.
- A project can switch in either direction at any time; the log then holds both forms (DL-093).
- A 1.0 CLI warns about the unknown key and creates sequential IDs (DL-079).
