## Context

Annotation scanning (DL-019) covers every tracked or unignored file outside a fixed list of build and dependency directories. Documentation and test fixtures legitimately contain example annotations. In this repository, `/dld-audit` reads about 40 examples in the README, `docs/concept/`, the SKILL.md files and the bats fixtures as real references to dld-kit's own decisions, and IDs as high as DL-091 will collide with real records as the log grows. Renumbering examples only postpones the problem. Other projects have the same issue with docs or generated code.

## Decision

- `dld.config.yaml` gains an optional `annotation_exclude` key: a list of git glob patterns relative to the project root, e.g. `docs/**`, `README.md`, `tests/**/*.bats`. It defaults to an empty list, and a non-list or a non-string entry is a config error (DL-009).
- The scanner passes each pattern to `git ls-files` as a `:(exclude,glob)<pattern>` pathspec, so matching follows git's glob rules (`*` stays within a directory, `**` crosses directories).
- The exclusions apply wherever the scanner is used: `find-annotations` and `verify-annotations`.
- dld-kit's own `dld.config.yaml` sets it for its documentation, SKILL.md examples and bats fixtures.
- `docs/framework/project-configuration.md` documents the key.

## Rationale

- Excluding by path fixes the problem once for any number of examples, instead of renumbering them every time the log grows.
- Delegating matching to git's pathspecs gives well-defined, documented glob semantics with no glob code of our own.
- Applying the list in the one scanner keeps `find` and `verify` consistent.

## Consequences

- An annotation in an excluded path no longer satisfies `verify-annotations`. That is the point; a project that excludes too much will see "missing annotation" failures, which makes the mistake visible.
- The bash scripts ignore the key. That gap closes when the skills switch to the CLI (workstream 7).
