## Context

A real OpenCode run wedged after item 1: the agent implemented DL-070, committed, and ended its turn asking "Ready for item 2 — Proceed?" The loop never dispatched item 2. Two compounding gaps caused it.

**Gap 1: the agent didn't drive the state machine.** The agent marked the decision accepted in its record and committed, but never ran the state scripts — no set-item-status, no evidence, no verify claim. In state.json the item stayed `implementing`. The dispatch messages say "as the dld-run skill describes," which assumes the dld-run skill is loaded in the project. In this project it wasn't, so the agent improvised its own completion ritual and the run state never advanced.

**Gap 2: the dispatch guard deadlocks on in-flight items.** The guard (DL-020) suppresses re-delivery of an item the session was already told to work. That kills the spam — but it also kills legitimate re-delivery when a turn ends without advancing the item: rate limit, context boundary, or the agent asking a question instead of continuing. The item stays in-flight forever, the guard suppresses forever, and the run is wedged.

The Pi extension avoids both: its continuation arrives as a hidden follow-up the agent acts on immediately, and the skill is guaranteed present because pi loads it from the same package.

## Decision

**Bounded re-delivery.** The loop tracks consecutive suppressed dispatches per session+item. The first time a turn completes with the item unchanged, the loop re-delivers it once — the turn may have ended for reasons unrelated to the work. If the next turn also ends without advancing, the loop stops re-delivering and surfaces a synthetic message: the item appears wedged, and the user should inspect or pause. Never two re-deliveries in a row; the anti-spam property holds.

**Inline operational instructions.** The dispatch prompt carries the state-machine protocol directly, so a run works in projects without the dld-run skill loaded:

- Claim the item: set-item-status implementing (already done by the loop) and work it
- When the work is done: set-item-status verifying, then add evidence via the scripts (evidence is what triggers the plugin's verification)
- Never mark an item accepted yourself — the plugin runs verification and the accept transaction
- To report a blocker: block-item with a reason
- End the turn when the state is updated; the loop continues from there

The prompt stays short — protocol steps, not the full skill text. The skill remains the right home for rationale and review flow; the dispatch needs only the mechanics that advance state.

## Rationale

The guard's purpose is preventing identical consecutive dispatches, not preventing recovery. One re-delivery distinguishes "agent is mid-work across turns" (rare, and the user sees one duplicate) from "agent is ignoring the work" (the wedge message fires). Two turns of no progress is strong evidence of a wedge; one is noise.

Inline instructions follow DL-019's lesson: any message that reaches the agent is agent context, and the agent acts on what's in context. "As the skill describes" is a dangling reference when the skill isn't loaded — the loop's correctness can't depend on content it doesn't control.

## Consequences

A run self-heals from single-turn stalls and tells the user when it can't. Projects without the dld-run skill get correct loop behavior; projects with it get identical behavior, since the protocol matches the skill's mechanics.

The wedge message is a new user-visible state between "running" and "paused": the run stays active, the loop stays quiet, and the user decides. This is deliberate — pausing automatically would hide the distinction between a blocked item (needs an answer) and a wedged agent (needs a nudge).
