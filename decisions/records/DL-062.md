## Context

DL-058 ships release candidates from `v1` and merges `v1` into `main` only for 1.0.0. Three candidates later, `main` still serves the 0.x skills and their bash scripts. Every channel that reads the default branch or the "latest" version therefore installs 0.x, which is now worse than the current candidate:

- The Claude Code, Codex and Copilot CLI marketplaces, and `npx skills add jimutt/dld-kit`, read `main`.
- `npx dld-kit init` and `pi install npm:dld-kit` install the npm `latest` dist-tag, which still points at `1.0.0-rc.1`. The release workflow publishes each candidate under `next` (DL-052).
- `gh skill install jimutt/dld-kit` installs the latest GitHub release, else the default branch. Prereleases do not count as latest, so it installs v0.9.0.

The project owner judges the current candidate a better install than 0.x for anyone, while 1.0.0 still waits for the candidates to run clean.

## Decision

- **Merge `v1` into `main` now** (PR #76). The merge is a fast-forward. `main` becomes the release branch for the remaining candidates and for 1.0.0, and `v1` is retired: CI stops triggering on it.
- **The README says the project is in release candidates.** The "Early development" note is replaced by one saying that 1.0 is in release candidates, which replace the 0.x skills, and that commands, file formats and skills may still change before 1.0.0. It links the last 0.x release, v0.9.0.
- **Each candidate becomes the default install.** After the release workflow publishes a candidate, the maintainer:
  - points the npm `latest` dist-tag at it (`npm dist-tag add dld-kit@<version> latest`);
  - marks its GitHub release as the latest release rather than a prerelease (`gh release edit v<version> --prerelease=false --latest`).

  Both steps stay manual; the workflow is unchanged. `next` keeps pointing at the newest candidate.
- **1.0.0** still waits until the candidates run clean (DL-058). The remaining steps are to release it from `main`, remove the release-candidate note, and mark docs/plan/v1.md as done.
- **Docs.** `docs/releasing.md` names `main` as the release branch, lists the two manual steps, and drops the `#v1` marketplace refs from the per-agent checks. The Codex and Copilot CLI marketplace checks can run on each candidate.
- **Refinements during implementation.**
  - `decisions/PRACTICES.md` names `main` as the branch PRs target.
  - The CI trigger line (`branches: [main]`) carries both DL-058's and DL-062's annotations.

## Rationale

- An install that works with known rough edges beats an install of a version whose scripts 1.0 replaces.
- Keeping `latest` and the GitHub "latest" release on the candidate makes every channel agree on one version.
- The npm and GitHub steps need the maintainer's credentials, so they stay out of the workflow.

## Consequences

- Marketplace and `npx skills` users get candidate versions as they are merged to `main`, including any changes before 1.0.0.
- A forgotten manual step leaves `npx dld-kit` or `gh skill` on an older candidate.
- Amends DL-058 (the release branch and when `v1` merges into `main`).
