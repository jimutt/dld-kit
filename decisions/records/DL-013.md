## Context

DL-008 committed continuation to `agent_end` gated on idle and pending messages. Live testing against the real harness — print mode, RPC mode, and reading pi's `agent-session.js` — surfaced three facts the original record did not know:

1. `ctx.isIdle()` is `!_isAgentRunActive`, and the flag clears only at `agent_settled`. At `agent_end` it is false in every mode, so an idle gate at event time can never pass.
2. pi invalidates the extension runtime when a session is disposed (print, RPC) or reloaded. An `agent_end` handler still awaiting script calls at that point dies with a stale-ctx error on every dispatch.
3. pi-goal-pro, the closest production prior art, does neither of the things I first wrote: it schedules with a `setTimeout`, returns from the handler immediately, and the deferred callback re-checks gates and dispatches through `pi.sendMessage({ triggerTurn: true })`.

## Decision

Amend DL-008's continuation mechanics to the scheduled-dispatch pattern:

- `agent_end` remains the trigger event, but the handler never awaits. It schedules a short timer (100ms), clears any prior timer, and returns.
- The deferred callback re-checks suspension and pending messages, runs the gate chain, and dispatches via `pi.sendMessage({ customType: "dld-goal:continuation", display: false }, { triggerTurn: true, deliverAs: "followUp" })`. A custom message, not a user message: it stays out of the visible transcript.
- The `isIdle()` gate is dropped at event time because it is definitionally false at `agent_end`; pending-user-input and the on-disk run status are the real guards.
- User suspension is explicit state: any `input` event suspends, `/dld-goal resume` and `/dld-goal start` clear suspension and dispatch immediately, so a loop never waits for a turn that may not come.

## Rationale

The timer pattern is the only shape that survives every pi mode: the handler returns before session teardown, the deferred callback fires after the run unwinds, and dispatching with `triggerTurn` starts a fresh agent run rather than relying on the current one draining its queue.

## Consequences

Continuation has a ~100ms delay instead of being immediate. User suspension is now real rather than aspirational — typing anything stops the loop until resumed, which is the behaviour DL-008 always promised.

The fake harness's `emit` waits a beat after handlers return, so deferred dispatches are visible to tests without each test managing timers.
