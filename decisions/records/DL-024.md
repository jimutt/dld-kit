## Context

Two independent reviews of the v1 extensions (one framework-architecture lens, one keep-it-simple lens) converged on the same finding: the biggest gap is not missing extractions — it is that the pi extension never adopted the mutation half of dld-core. dld-core's Exec is synchronous (execFileSync); pi's exec is async. So loop.ts and index.ts re-implement the seam with a private runScript/MutationEnvelope and duplicate activeRun/resumableRun line-for-line. DL-022's "both extensions migrate to the library" is only half-done.

The duplication has already drifted into bugs on the pi side:

1. Pi's start path leaves a half-populated run ACTIVE when add-item fails mid-loop. OpenCode's rollback (set blocked + event) was written specifically against this; pi never got it.
2. Pi pauses/resumes/stops without writing events. activeMinutes derives from run-paused markers, so paused time counts as active and maxMinutes fires early.
3. Pi's verify treats any non-zero exit as a failed attempt. run-api maps timeouts to exit code 3 (infrastructure, not a test failure); pi never consumes the distinction, so an item can block because its test suite ran long.

Both reviews also flagged that opencode-dld-run has zero tests — extraction into core is the only way that logic gets tested.

The user reviewed both reports and chose the extraction set, adding the DispatchGuard (which the pragmatist reviewer would have deferred) to the do-now list.

## Decision

Extract into dld-core, in dependency order:

**1. Async Exec unification (the prerequisite).** Widen core's Exec to allow Promise<ExecResult>. run-api functions become async. Pi's loop.ts and index.ts delete runScript/MutationEnvelope and call run-api directly through pi.exec. OpenCode keeps defaultExec.

**2. Lifecycle operations with status+event pairing.** pauseRun, resumeRun, stopRun, completeRun as core functions that set the status AND append the event. Fixes pi's activeMinutes corruption by making the pairing a core invariant instead of per-harness discipline.

**3. startRun with rollback.** guard → create → add items → on failure: set blocked + event (OpenCode's behavior becomes canonical) → first dispatch. Fixes pi's half-populated ACTIVE run.

**4. CompletionTracker.** The completion transaction (find verifying item with new evidence → verify → pass+review-nag / pass+accept→repin→event / fail+retry / fail+block+pause) as a core class holding verifiedAtEvidence and reviewNagged, returning a discriminated-union outcome the harness renders. Fixes pi's missing infrastructure branch. Pi's loop tests port to core as the acceptance gate.

**5. boundsExceeded.** Pure function over state + events returning maxItems/maxMinutes/null. Closes OpenCode's maxMinutes gap (a promise the direction doc already made).

**6. projectRootOf + runDir.** Consolidate the four projectRoot implementations and the six join(root, ".dld", "runs", slug) copies into paths.ts.

**7. DispatchGuard as a pure state machine.** The lastDispatch/redispatched/wedged trio from server.ts, extracted as classify/record/clearSession/clear. Pi adopts it too — pi currently re-dispatches the in-flight item every agent_end relying on hidden-followUp delivery to mask it, which is the same wedge risk DL-023 fixed for OpenCode.

Explicitly NOT extracted: the loop driver / LoopEffects framework, the run observer abstraction, message delivery, suspension/token policy, TUI rendering, session→root mapping, dispatchText (stays OpenCode-specific per DL-023's reasoning).

## Rationale

The ordering is dependency-driven: nothing else works until pi can consume run-api (item 1). Items 2-6 are small, pure, and each closes a concrete bug or gap. The CompletionTracker (item 4) is the biggest and correctness-critical — it is the DL-003/DL-021 invariant maintained twice by hand.

The DispatchGuard inclusion over the pragmatist's objection: the wedge risk on pi is real (an agent_end that doesn't advance the item re-dispatches identically, and the hidden followUp masks it from the user), the guard is ~40 lines of pure in-memory logic, and extracting it now costs less than waiting for pi to wedge in production.

The loop driver is excluded because two call sites with genuinely different sequencing (pi's token+timer vs OpenCode's per-session guard) is the over-abstraction trap. Revisit when a third harness exists.

## Consequences

Pi's extension shrinks by ~200 lines and adopts the verify-timeout policy, the infrastructure branch, and event-paired lifecycle transitions by construction. OpenCode's server.ts shrinks by ~230 lines and gains test coverage via core-level bun tests. Both harnesses enforce identical semantics for the completion transaction, lifecycle events, and the dispatch guard.

Pi's behavior changes deliberately in three places: events are now written on pause/resume/stop (closer to the run contract), a failed start blocks the run instead of leaving it half-active, and verify timeouts no longer burn attempts. Each is a fix, and each is documented in its commit.

The loop driver and run observer stay out. The core's public surface after this work is the npm package's API: state reading, mutations, the transaction, bounds, the guard, rendering, and path resolution — everything except delivery and lifecycle wiring, which remain the harness's defining characteristics.
