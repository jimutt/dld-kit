## Context

1.1 adds timestamp IDs (DL-092). Only the exact spelling is an ID, so `DL-T1K3M9Z2P7XQ4` in upper case, or `DL-5` for `DL-005`, names nothing. `create-decision` and `plan-renames` already name the canonical spelling when given another one (DL-078). The commands that take IDs as arguments did not: `related-decisions`, `check-decision-edits` and `restore-decision-prose` said only "expected decision IDs like DL-001", which describes the sequential form alone, and `update-status` and the other lookups said only "decision DL-5 not found". `docs/id-formats.md` tells users the tools say so when a spelling is wrong.

## Decision

- A usage error for an argument that is not a decision ID names both forms, `expected decision IDs like DL-001 or DL-T1k3m9z2p7xq4, got '<arg>'.`, and adds ` Did you mean <canonical>?` when the argument is another spelling of a valid ID.
- A "decision <id> not found." error adds the same hint when the canonical spelling differs from what was given.
- The hint comes from `canonicalSpelling` in `src/core/ids.ts`; the messages are built there (`spellingHint`, `notAnIdMessage`), so every command words them the same way.
- Exit codes do not change.

## Rationale

Agents retype IDs, and an upper-case or unpadded ID is the likeliest mistake. Naming the canonical spelling turns a dead end into a one-step fix, which is what the docs already promise. Keeping the wording in the ID module follows DL-093: one place knows how IDs are spelled.

## Consequences

- Error text changes for these commands; the commands the skills run are internal (DL-056), so this needs no major release.
- The lookup itself stays exact: a non-canonical spelling is still not found, only explained.
