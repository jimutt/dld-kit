## Context

`dld.config.yaml` is parsed into a validated config (DL-009), but keys the parser does not know are ignored without a word. A typo such as `decision_edit: allow` leaves the default `block` in force, and the user believes they changed the setting. Making unknown keys an error after 1.0 would break configs that work today, so the behaviour has to be settled now.

## Decision

- Parsing the config reports warnings. A top-level key that is not part of the configuration spec produces `dld.config.yaml: unknown key '<key>'`, followed by `; did you mean '<known key>'?` when a known key is within two edits of it.
- `Context` gains `warn(message)`, the channel core uses for problems that do not stop a command. The CLI dispatcher prints each distinct message once per run as `Warning: <message>` on stderr, so every command that loads the config reports the warnings without code of its own, and carries on. Stdout and exit codes are unchanged.
- Unknown keys stay warnings in every 1.x release. Only a major version could make them errors.
- The configuration spec says that unknown keys are reported, and lists every key.

## Rationale

- A warning catches typos at the first command without breaking configs that hold keys from a newer dld-kit or from other tools.
- Deciding before 1.0 that unknown keys only ever warn leaves later releases free to add keys.

## Consequences

- A config written for a newer dld-kit warns when an older CLI reads it. That is accurate: the older CLI ignores those keys.
