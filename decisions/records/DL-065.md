## Context

Stacking is the normal DLD flow: decisions go up as one PR, and implementation branches are cut from it. Such a branch adds, compared with the base, every record from the decisions PR, and the open-PR scan (DL-026) reports the same IDs as claimed by that PR. So `find-collisions` lists every decision the branch exists to implement, and `plan-renames` would renumber them, away from the PR they came from.

PR #53 fixed this in the pre-1.0 bash scripts on the `dld-run` branch: `list-taken-ids.sh --exclude-contained` skips open PRs whose head branch is an ancestor of HEAD, and `find-collisions.sh` passes that flag. The PR was never merged, and the scripts have since been ported to the CLI (DL-026, DL-027).

## Decision

- The open-PR scan also reads each PR's `headRefOid` and returns every claimed ID together with that PR's head commit.
- A record this branch adds does not collide with an open PR's claim when the commit that added the record on this branch (the latest commit in `<base>..HEAD` that adds the path) is the PR's head commit or one of its ancestors. The record came from that PR, so it is the same decision, not a second claim.
- Testing the record's own commit, rather than whether the PR's head is an ancestor of HEAD as PR #53 does, also covers a decisions PR that got more commits after the implementation branch was cut.
- When the PR's head commit is not in the local repository (not fetched, or a fork), ancestry cannot be checked and the claim counts as a collision. The skill runs `git fetch origin` first.
- IDs on the base branch are collisions as before.
- `list-taken-ids`, and the ID allocation in `plan-renames`, still count every claim: a stacked PR's IDs are taken, so new IDs go above them.
- The PR from the current branch is still skipped, per DL-026.

## Rationale

A collision means two different decisions want one ID. When this branch's record came from the PR, there is one decision and one claimant. Git ancestry answers "came from" exactly; comparing IDs or branch names cannot tell a stacked branch from an unrelated one.

"Taken" and "collides" are different questions. An ID from the PR below is not a conflict, but it is in use, and handing it out again would duplicate it.

Treating an unknown head commit as foreign means a missing fetch can only cause a false collision, never hide a real one.

## Consequences

- Stacked implementation branches report no collisions for the records they share with the PR below.
- A record that reached this branch by cherry-pick, or from a PR that was rebased after the branch was cut, still reports a collision.
- Once the PR below is squash- or rebase-merged, its records are on the base under new commits, and this branch's copies collide with the base. The fix is to merge the base into the branch, after which nothing collides. The code does not detect this case; the skill tells the agent to compare each colliding record with the base's copy and, if they are the same decision, stop and ask the user to merge the base first.
- The commit lookup passes `--no-follow` and `--no-show-signature`, so `log.follow` or `log.showSignature` in the user's git config cannot change its output.
