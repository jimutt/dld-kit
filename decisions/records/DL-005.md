## Context

Long-running execution needs two things that live at different layers: DLD semantics (which decisions, in what order, verified how) and loop mechanics (continuing after the agent stops, rotating context, surviving restarts, showing progress).

DLD ships to multiple harnesses — Tessl-installed skills, Claude Code, and Pi. Loop mechanics require harness lifecycle APIs that only Pi exposes. Building them into the skill would either make the skill Pi-only or produce a skill that pretends to control a loop it cannot actually drive.

The surveyed extension that handles this best (`pi-autoresearch`) draws the line explicitly: the extension supplies measurement, logging, continuation, and UI; the skill elicits domain intent and writes the contract.

## Decision

The `/dld-goal` skill owns DLD semantics and nothing else: contract authoring, item ordering and batching, the completion transaction, blocked-item escalation, and run reporting. It contains no loop machinery. In a harness without the extension it runs as a manually paced loop — the agent works items in sequence within a conversation, the developer nudges it along.

The Pi extension owns mechanics: `/dld-goal` command surface, `agent_end` continuation with idle and pending-message checks, run tokens against stale dispatch, child-session rotation per item, deterministic compaction rebuilt from run state and decision records, the status widget, and stale-owner recovery.

Both read and write the same files in `.dld/runs/`. A run started manually can be continued by the extension and vice versa.

The extension lives in this repository under `extensions/`, published as an npm package with `package.json#pi.extensions`.

## Rationale

The contract files are the interface. Keeping them the only coupling means the skill stays portable and the extension stays replaceable — a future harness gets its own mechanics layer without touching DLD semantics.

The skill is built first, and alone, because it holds the semantics that are hard to get right. Mechanics are commoditised: `agent_end` continuation, run tokens, atomic snapshots, and append-only ledgers are well-established patterns across a dozen implementations. Designing the mechanics against a proven contract is far cheaper than designing both at once.

In-repo rather than a separate package because every contract change would otherwise need cross-repo coordination, and the two halves are useless apart. The cost is a TypeScript and npm artifact in a repo that is currently markdown and bash, which is contained under `extensions/`.

## Consequences

Without the extension, `/dld-goal` is a paced workflow rather than an autonomous loop. It is genuinely useful — contract, ordering, gating, and reporting all work — but the developer supplies the continuation. This must be stated plainly so the skill is not oversold.

The repo gains a build and publish path it does not have today, along with the maintenance that implies. Confined to `extensions/`; the skills and scripts stay dependency-light.

Two implementations of the state transitions will exist — bash with `jq` in the skill, TypeScript in the extension. They must agree. The schema needs to be specified precisely enough that they cannot drift, and cross-checked by tests on both sides.
