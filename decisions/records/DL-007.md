## Context

The 1.0 plan proposes a TypeScript library plus a thin `dld` CLI (docs/plan/v1.md). PRACTICES.md says the library holds the logic and the CLI parses arguments, calls the library and formats output. DL-002 makes the CLI the only public contract. The toolchain slice left a single `src/cli.ts`. Before any script is ported, the boundary needs to be concrete so each port lands in the right place.

## Decision

- `src/core/` holds the logic: config, paths, IDs, and later records, index, annotations, audit, snapshot, reindex. Core functions take their inputs and an injected context, and return values or throw `DldError`. Core never writes to stdout or stderr, never reads `process.argv` or `process.env` directly, and never calls `process.exit` or sets `process.exitCode`.
- `src/cli/` holds the command layer: dispatch, one module per command, argument parsing, output formatting, and mapping errors to exit codes. `src/cli.ts` moves to `src/cli/`.
- `src/bin.ts` stays the only entry point that touches `process`. It builds the real context and calls the CLI.
- Core does not import from `src/cli/`.

## Rationale

- A library that never prints or exits can be unit-tested directly and reused by `dld init`/`dld update` and the generator later.
- One module per command keeps each port small and reviewable, and maps one-to-one onto the script being replaced.
- Keeping `process` access in one file makes Node/Bun differences and test isolation easy to reason about.

## Consequences

- Every command has two parts: a core function and a CLI wrapper. That is more files than a direct port, but each is small.
- The core API is internal (DL-002), so it can be reshaped freely during the port.
