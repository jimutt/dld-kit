## Context

`dld.config.yaml` is committed and shared by the team. Some settings are personal: which model reviews a developer's changes, or whether they want a review of their plans, depends on their harness, their budget and the task. Today a developer who wants a different review model says so in every `/dld-implement` request. dld-kit-next, the lab copy, already keeps per-checkout settings in a gitignored `dld.local.yaml` at the repository root.

## Decision

- A project may have `dld.local.yaml` at the repository root, next to `dld.config.yaml`. It holds one developer's settings for that checkout and is never committed.
- It accepts only personal settings: `implement_review`, `plan_review`, `review_model`, `implement_review_model` and `plan_review_model`, plus keys starting with `x-`. Values follow the same rules as in `dld.config.yaml`. Any other key, including team settings such as `decision_edits` or `base_branch`, is ignored with a warning: `dld.local.yaml: '<key>' can only be set in dld.config.yaml` for a config key, or the unknown-key warning (DL-079) otherwise.
- A missing file means no overrides. A file that is not valid YAML or not a mapping, or that holds an invalid value, fails the command that reads it with an error naming `dld.local.yaml`.
- Precedence, highest first: what the user asks for in their message for that run; `dld.local.yaml`; `dld.config.yaml`; the built-in default.
- `dld init` and `dld update` make sure git ignores `dld.local.yaml`: if `git check-ignore` does not already match it, they append it to the root `.gitignore`, creating the file if needed, under a comment saying what it is, and report the change.
- The file name and the keys it accepts join the public contract (DL-085).

## Rationale

- A gitignored file next to the config is the convention the lab already uses, and it is where a developer looks for project settings.
- Limiting the file to personal settings keeps team policy in the reviewed, shared config: one developer's local file cannot loosen `decision_edits` for their own changes without anyone seeing it.
- Checking with `git check-ignore` respects an existing global or nested ignore rule instead of adding a duplicate line.

## Consequences

- Projects get one more line in `.gitignore` on their next `init` or `update`.
- A dld-kit-next checkout whose `dld.local.yaml` holds other keys, such as `paths`, sees a warning from the commands that read the file until those keys are part of dld-kit or use the `x-` prefix.
