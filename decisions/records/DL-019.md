## Context

The spike's command handler implemented status, pause, resume, and stop — operations on an existing run — but not start. The first thing a user types is `/dld-run start DL-X DL-Y`, and the plugin answered "Unknown subcommand" via a synthetic message. The agent then saw that message in context and began exploring the filesystem to diagnose the failure, turning a simple gap into a confusing user experience.

Two lessons: the command surface must cover the full run lifecycle from the start, and an unhandled subcommand should fail silently for the agent (or not reach the agent at all), not produce a message the agent has to interpret.

## Decision

Implement `start` in the OpenCode server plugin, mirroring the Pi extension's flow: parse decision arguments (range, dash, positional forms), run guard-preconditions, create the run, add items with hash pinning, and dispatch the first item immediately.

Unhandled subcommands return a synthetic message marked clearly as a plugin response, so the agent relays it verbatim instead of investigating.

## Rationale

The Pi extension's parseStartArgs handles DL-014..DL-022, DL-014 - DL-022, and positional forms. That logic is pure string parsing and ports directly. The script calls (guard-preconditions, create-run, add-item) are the same calls the Pi extension makes.

The synthetic-message failure mode is a general design principle for plugin-driven loops: any message injected into the session becomes agent context, and the agent will act on it. Error messages meant for the user should be phrased so the agent's correct action is to repeat them, not to debug them.

## Consequences

The plugin's command surface covers the full lifecycle: start, status, pause, resume, stop. The start flow is the heaviest command — it validates preconditions, creates the run directory, pins decision hashes, and kicks off the loop.

This amends DL-017's spike scope: the command surface was underspecified there, and the start gap was discovered by the user's first interaction.
