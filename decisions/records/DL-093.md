## Context

Many commands sort by the ID's number: `INDEX.md` (DL-018), `collect-active-decisions` and the snapshot change lists (DL-025), `list-taken-ids` and the rename plan (DL-027), `related-decisions` (DL-077), `list-proposed` and `find-missing-amends`. Core carries the number as `recordNumber` and `number` fields in seven modules. A timestamp ID (DL-092) has no number, and a log can hold both forms.

## Decision

- One comparison orders all decision IDs:
  1. Sequential IDs come before timestamp IDs.
  2. Sequential IDs are ordered by number, and IDs with the same number (`DL-01`, `DL-001`) by text, as now.
  3. Timestamp IDs are ordered as text.
  4. A value that is neither sorts last, by text.
- Every place that orders decisions by ID uses it: the index (descending), `collect-active-decisions`, `detect-snapshot-changes`, `list-taken-ids`, `find-collisions`, `plan-renames`, `related-decisions`, `list-proposed` and `find-missing-amends` (all ascending).
- Core has one module for IDs. It parses an ID into its form, compares IDs and gives the ID of a record file. No other module reads the digits of an ID or spells an ID pattern.
- Output for a log with only sequential IDs does not change.

## Rationale

- Records created after a project switches form are timestamp IDs, so putting them after the sequential ones keeps the log roughly chronological without reading every record's `timestamp`.
- Fixed-width base32 time sorts as text, so no decoding is needed.
- One module is what makes a third form, or a change to this one, a local change.

## Consequences

- The order is a convention, not creation order. A sequential ID can be newer than a timestamp ID: a branch that was open during the switch, or a collaborator on a 1.0 CLI. Nothing may depend on ID order being chronological.
- File browsers agree with this order for timestamp IDs, and still disagree for `DL-999` and `DL-1000`.
