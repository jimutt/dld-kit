## Context

`/dld-plan` breaks a feature into several proposed decisions. For large or complicated features, developers sometimes ask for a separate agent to review the plan before implementing it, the way `/dld-implement` reviews code. A plan's mistakes are cheapest to fix while its decisions are still proposed: a gap, a decision that conflicts with an accepted one, a missing amendment, or a choice too vague to implement.

## Decision

- A new setting, `plan_review` (boolean, default `false`), in `dld.config.yaml` and `dld.local.yaml` (DL-087). The user can also ask for or skip a plan review in their message for that run.
- When the review is on (`dld review-settings plan`, DL-088), `/dld-plan` launches a review subagent after creating the records and checking them for unstated relationships, before checking decision edits. It runs on the model DL-088 resolves.
- The reviewer reads the feature description, the new records, the related decisions the skill found, and `PRACTICES.md`, and reports findings by severity (critical, moderate, minor) on:
  - coverage: parts of the feature no decision covers;
  - granularity: decisions that bundle several choices, or that are only "build X";
  - conflicts and relationships: overlap or contradiction with existing decisions, and `amends` or `supersedes` that are missing or wrong;
  - vagueness: values, limits or behaviour the implementer would have to guess;
  - order: dependencies between the decisions;
  - practices: anything the project's `PRACTICES.md` rules out.
- The planning agent fixes critical and moderate findings in the new records, which are drafts, and asks the user with `AskUserQuestion` when a fix would change what a decision means. Minor findings are optional. As with the implementation review, the skill states that enabling the setting and running the skill is the user's request for the subagent; if the subagent cannot run, the agent reviews inline and says so. The final report says whether the plan was reviewed, by which model, and what changed.

## Rationale

- An opt-in review costs nothing for small plans and gives large ones a check from an agent that did not write them.
- Off by default, because plans are usually small and the implementation review already runs by default; teams that plan large features can turn it on for everyone, and individuals for themselves.
- Fixing drafts in place, and asking only when the meaning changes, keeps the developer in charge of what was decided.

## Consequences

- A reviewed plan takes longer and costs one more agent run.
- `plan_review` joins the public contract (DL-085).
