## Context

Fresh context per work item is the strongest hygiene pattern in the ecosystem survey: the item gets only what it needs, and nothing leaks between items except what is written to disk. It is what ralphi and Huntley's original loop do.

Pi restricts session control to command handlers. `newSession`, `fork`, and `switchSession` exist on `ExtensionCommandContext`, not on the context passed to event handlers, and the documentation states why: "These are only available in commands because they can deadlock if called from event handlers."

That rules out driving rotation from `agent_end`. Reading how ralphi resolves this was decisive, because the obvious workaround — a command handler that loops and awaits idle between items — is not what it does.

## Decision

Child-session rotation is re-entrant, not a long-lived handler:

1. A command (`/dld-goal run`) validates preconditions, records the current session as the controller session, and starts the first iteration.
2. Starting an iteration switches to the controller session, selects the item, calls `ctx.newSession({ parentSession })`, names the child, and sends the item brief. The command handler then returns.
3. The `ExtensionCommandContext` is retained in a map keyed by iteration, deliberately outliving the command that created it.
4. The child signals completion through a typed tool, never through prose or a marker string.
5. The tool handler retrieves the stored context, switches back to the controller, and — if the run continues — starts the next iteration. That recursion is the loop.

Every programmatic session switch is wrapped so the extension suppresses its own `session_start` state restoration while switching.

**Completion is verified, not trusted.** The tool call means "I claim this item is done". Before advancing, the extension re-reads `state.json` and requires the item to be `accepted`. A claim without the corresponding disk state does not advance the run; it reports the discrepancy and pauses.

## Rationale

The re-entrant shape is taken from ralphi's `loop-controller.ts` and `loop-finalizer.ts`, where `finalizeLoopRun` ends by calling `runLoopIteration` again. It avoids a blocked handler holding the harness open for the length of an entire run, and it survives the child agent taking arbitrarily long.

Suppressing state restoration during switches is also taken from ralphi (`withSuppressedEventRestore`): a switch fires `session_start`, which would otherwise restore stale persisted state over live in-memory loop state.

Verifying the claim against disk is where this deliberately diverges from ralphi, which marks a story done from the tool payload. The prior-art review flagged that as its weakest link. DLD does not need to trust a claim: item status is deterministic on disk, written by the same verified transaction in both paced and autonomous modes.

## Consequences

Rotation only starts from a command. The extension cannot silently upgrade an in-session run into a rotating one from an event; the user asks for it explicitly.

Retaining a command context past its command is unusual and depends on pi tolerating it. It is what ralphi does in production, but it is a coupling to harness behaviour that a future pi release could change, and the integration tests must cover it.

A run spans several session files. Status output must point at the controller and the active child, or the user cannot find where the work is happening.
