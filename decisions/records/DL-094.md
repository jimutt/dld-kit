## Context

The scans match `DL-` plus digits: annotations and their near-misses (DL-074), mentions in record bodies (DL-082), the rewrite of a renamed ID (DL-029), IDs claimed by open PRs (DL-026) and the IDs given to commands as arguments. A timestamp ID (DL-092) matches none of them.

## Decision

- Wherever a decision ID is recognised in text or accepted as an argument, both forms are: the annotation scanner, `find-missing-amends`, the open-PR scan, `rename-decision`, `find-stale-mentions`, `commit-reindex`, and the ID arguments of `check-decision-edits`, `restore-decision-prose`, `related-decisions`, `verify-annotations`, `update-status` and `create-decision`. They take the pattern from the ID module (DL-093).
- **Annotation syntax.** The ID inside an annotation is a sequential ID, as now, or a timestamp ID in canonical form. A sequential ID that is not canonical still counts, as DL-074 decided. A timestamp ID in another spelling is not an annotation.
- **Near-misses** are also reported for text that starts like an annotation and contains `DL-T` or `dl-t` followed by a base32 character, in any letter case, and is not a valid annotation. That covers an upper-case key, a truncated one and one with spaces.
- **Where an ID ends.**
  - A sequential ID ends where the digits end, as now, so `DL-100` is not found inside `DL-1000`.
  - A timestamp ID is exactly 12 characters after the `T` and must not be followed by a lower-case letter or a digit. A longer run of such characters is not an ID and is not rewritten.
- A timestamp ID in a record body counts as a mention for `find-missing-amends`, with the DL-082 tiers unchanged.
- Rename rewrites keep the byte-preserving behaviour of DL-029 for both forms.

## Rationale

- One pattern source keeps the scans in step: an ID that one scan finds and another misses is how references go stale.
- The fixed length gives a timestamp ID a cheap, exact boundary. Requiring the canonical spelling in annotations keeps identity a plain text comparison.
- Sequential matching is left exactly as it is, so existing logs see no change in what counts as a mention.

## Consequences

- A typo in a timestamp ID almost always produces an ID that does not exist, which `verify-annotations` and the audit report as an orphan. Agents should copy IDs from command output, not retype them.
- Prose that happens to contain `DL-T` and 12 valid characters would be read as an ID. English words that long nearly always contain `i`, `l`, `o` or `u`.
