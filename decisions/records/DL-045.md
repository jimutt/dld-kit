## Context

The always-on rule (look up `@decision` annotations before changing annotated code; never contradict a decision silently) is DLD's core feedback loop and must be in context without the user invoking a skill. No distribution channel carries it today; `templates/rules/dld-workflow.md` holds the text and the dld-init skill appends a copy to CLAUDE.md by hand. Harnesses differ (DL-041):

- Claude Code loads owned files in `.claude/rules/`.
- Antigravity loads owned files in `.agents/rules/` marked `trigger: always_on`.
- Codex has only AGENTS.md, with no include mechanism.
- Pi and OpenCode read AGENTS.md, falling back to CLAUDE.md when there is none.

OpenSpec 1.0 stopped writing marker blocks and relies on skills alone, but its workflows are user-triggered. Spec Kit and BMAD keep a managed block in AGENTS.md; superpowers injects its text from a Claude plugin `SessionStart` hook.

## Decision

- **Text.**
  - `templates/rules/dld-workflow.md` is the one source for every channel.
  - It names skills rather than slash commands ("look up the decision with the dld-lookup skill"), because invocation syntax differs: Pi uses `/skill:dld-lookup`.
  - It keeps annotation examples in code spans, because Claude Code and Antigravity treat a bare `@path` as a file reference.
- **Owned rule files.** dld-kit owns these files outright and rewrites them on every update. Each carries the DL-044 notice with its version.
  - Claude Code: `.claude/rules/dld-workflow.md`.
  - Antigravity: `.agents/rules/dld-workflow.md`, with frontmatter `trigger: always_on`.
- **Managed block.**
  - For Codex, Cursor, OpenCode and Pi, a block between `<!-- dld-kit:start -->` and `<!-- dld-kit:end -->` holds the text and a version stamp.
  - It goes in the instructions file those harnesses read: AGENTS.md if it exists, else CLAUDE.md if it exists, else a new AGENTS.md. Creating AGENTS.md next to CLAUDE.md would make Pi and OpenCode stop reading CLAUDE.md.
  - When the block goes in CLAUDE.md, dld-kit warns that Codex reads only AGENTS.md.
- **Once per harness.** A harness that already loads the file holding the block gets no owned rule file, and a stale one is removed:
  - Claude Code, when the block is in CLAUDE.md, or in AGENTS.md with no CLAUDE.md.
  - Antigravity, when the block is in AGENTS.md.
- **Editing the block.**
  - The block is replaced in place, and the rest of the file stays byte-identical, including its line endings.
  - When there is no block yet, it is appended after a blank line.
  - A start marker without an end, an end before a start, or more than one block is an error naming the file, and nothing is written.
- **Command.**
  - `dld install-rule --agent <names>` does only the rule step. `init` and `update` call the same library code.
  - Because the rule text is embedded in the bundle (DL-042), the command works from any copy of the CLI, including the one inside `dld-common`.
- **Plugins and extensions.** A Claude plugin `SessionStart` hook, a Pi extension, an OpenCode plugin, or an Antigravity plugin's `rules/` deliver the same text. They are built with the plugin work in workstream 9.

## Rationale

- Owned files where a harness supports them avoid editing files the user writes. Nothing else touches them, so updating them is a plain overwrite.
- A marker block is the only way to reach Codex, and the least surprising way to reach Pi and OpenCode. Markers make it updatable, unlike the old hand-written block.
- Loading the rule twice wastes context and invites the agent to treat the copies as different rules, hence the once-per-harness rule.

## Consequences

- dld-kit edits a user-owned file (AGENTS.md or CLAUDE.md) only between its own markers.
- The plugin channels in workstream 9 need no new text, only a way to print it.
