## Context

`commit-reindex.sh --base <ref>` reads the rename plan on stdin and rewrites branch history so that no branch commit ever adds a colliding path, which would make `git rebase` fail with an add/add conflict:

1. Checks the base and the plan, and that HEAD is not already the merge-base.
2. Builds the stage list: the old and new path of every plan entry, plus every file changed on the branch (`git diff --name-only --diff-filter=AMRD <merge-base>..HEAD`), except `<decisions_dir>/INDEX.md`.
3. Records the original commit subjects and builds the message: `reindex local decisions: DL-A -> DL-B, ...` (or `reindex N local decisions to avoid base-branch collisions` for more than three), a `Renames:` list and a `Squashed from original branch commits:` list.
4. Mixed-resets to the merge-base, restores INDEX.md to its merge-base state (or removes it), stages each path with `git add -A -- <path>`, ignoring every failure, and commits. It prints `Created reindex commit <short> on top of <short>`.
5. On failure after the reset, an EXIT trap soft-resets to the original HEAD. The index and INDEX.md are left as the failed run left them.

With rename detection on (git's default), `--name-only` lists only the new name of a file renamed on the branch, so the deletion of its old path is not staged. Paths are passed as pathspecs, so a file name containing glob characters can stage other files.

## Decision

- `dld commit-reindex --base <ref>` keeps the script's steps, messages, stage-list rules, INDEX.md exclusion and commit message format. The plan is read and validated per DL-028.
- The branch's changed files are listed with `git diff -z --no-renames --name-only --diff-filter=AMRD <merge-base>..HEAD`, so both sides of a rename are staged.
- Staging runs `git --literal-pathspecs add -A -- <path>` per path, in sorted order. Only a path that is neither in the working tree nor in the index is skipped; any other `git add` failure fails the command.
- The commit is made with `git commit --quiet -m <message>`, so hooks and signing configuration apply as before.
- Before the reset, the command saves the original HEAD, the index as a tree (`git write-tree`, which also refuses an index with unresolved conflicts before anything changes), and the INDEX.md working copy (content or absence).
- If any step after the reset fails, it restores all three: `git reset --soft <original HEAD>`, `git read-tree <saved tree>`, and INDEX.md rewritten or removed. The error names the failed step and says the branch was restored. If the rollback itself fails, the error gives the original HEAD and the saved tree so the user can restore by hand.
- Once the commit succeeds there is no rollback.
- Tests cover each failure point with a fake git in the Context (reset, add, commit, and rollback failures), plus the bats hook-based failure test and a real-repo test that the restored state matches the pre-run state exactly.

## Rationale

- This command moves the branch; a failure must leave it exactly where it was. Restoring the index and INDEX.md as well as HEAD means a retry starts from the same state as the first attempt.
- `--no-renames` and literal pathspecs close two ways the explicit stage list could drift from what the plan and the branch diff name.

## Consequences

- Squashing still discards the branch's individual commits; their subjects are kept in the message, as before.
- A reindex whose branch renamed a file that existed at the merge-base now removes the old path in the squashed commit, which the script did not.
