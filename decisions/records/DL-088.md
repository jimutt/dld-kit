## Context

Teams are choosing models per task for cost: a cheaper model where it is good enough, a stronger one where it matters. `/dld-implement` runs a review subagent (`implement_review`), and developers often ask for a specific reviewer model, sometimes from a different vendor than their main agent, by writing it into every request. Model names are specific to each harness, and whether an agent can pick a subagent's model at all depends on the harness.

## Decision

- Three optional string settings, in `dld.config.yaml` and `dld.local.yaml` (DL-087): `review_model` names the model for review subagents; `implement_review_model` and `plan_review_model` override it for the implementation and plan reviews. A step's model is its own key if set, else `review_model`, else the harness's default. The names are passed on as written; dld-kit does not interpret them.
- A new internal command, `dld review-settings <implement|plan>`, prints the effective settings for a step, merging the two files under DL-087's precedence:
  ```
  review: on
  review_from: dld.config.yaml
  model: gpt-sol-6.1
  model_from: dld.local.yaml
  ```
  `review` is `on` or `off`; `model` is a name or `default`; the `_from` lines are `dld.local.yaml`, `dld.config.yaml` or `default`. `implement` reviews by default and `plan` does not (DL-089).
- `/dld-implement` and `/dld-plan` run it before their review step instead of reading the config themselves. A review or model the user asked for in their message for this run wins over the command's output.
- When the model is not `default`, the skill asks the agent to run the review subagent on it if its harness lets it choose the subagent's model and accepts that name. If not, the review runs on the harness's default and the agent says so. The report names the model that reviewed and where the choice came from.

## Rationale

- A shared default lets a team set its review policy once; per-step keys let it spend more on the step that needs it, without making the common case longer.
- Keeping model names as plain strings, with the agent deciding whether it can honour them, works in every harness: one that cannot choose a model still runs the review.
- Doing the merge in a command keeps precedence in tested code rather than in each skill's prose.

## Consequences

- A team whose members use different harnesses usually leaves `review_model` unset in the shared config and lets each developer set theirs in `dld.local.yaml`.
- The new keys join the public contract (DL-085).
