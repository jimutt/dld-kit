## Context

DLD's skills and always-on rule must reach the agent harnesses people use. Research in September 2026 (Claude Code, OpenCode, Pi and Antigravity docs and source) found two skill layouts and several rule mechanisms:

- Claude Code reads skills only from `.claude/skills/` and loads `.claude/rules/*.md` at startup like CLAUDE.md. It does not read `.agents/`.
- Codex, Cursor, OpenCode, Pi and Antigravity read `.agents/skills/`. Pi and Antigravity (and Gemini CLI) load project skills only in trusted folders.
- OpenCode also reads `.claude/skills/`, and picks between same-named skills nondeterministically (DL-046).
- For always-on text: Codex reads only AGENTS.md; Pi and OpenCode read AGENTS.md, falling back to CLAUDE.md; Antigravity reads AGENTS.md or GEMINI.md and supports owned rule files in `.agents/rules/` with `trigger: always_on`.
- Gemini CLI, replaced for most users by Antigravity CLI in May 2026, reads `.agents/skills/` but loads only GEMINI.md by default.

## Decision

- `--agent` takes harness names, comma-separated and repeatable. Each maps to a skill layout and a rule channel (DL-045):

| Harness | Skills | Rule |
|---|---|---|
| `claude` | `.claude/skills/` (claude-code adapter) | `.claude/rules/dld-workflow.md` |
| `antigravity` | `.agents/skills/` (agent-skills adapter) | `.agents/rules/dld-workflow.md` |
| `codex`, `cursor`, `opencode`, `pi` | `.agents/skills/` (agent-skills adapter) | managed block in the instructions file |

- Harnesses that share a layout or channel install it once.
- `dld init` detects harnesses from markers at the project root:
  - `claude`: `.claude/` or `CLAUDE.md`
  - `antigravity`: `.agents/rules/`, `.agent/` or `GEMINI.md`
  - `codex`: `.codex/`
  - `cursor`: `.cursor/`
  - `opencode`: `.opencode/`, `opencode.json` or `opencode.jsonc`
  - `pi`: `.pi/`
  - `AGENTS.md` or `.agents/skills/` with no more specific marker select the `.agents/skills/` layout and the managed block, as for `codex`.
- Selection in `dld init`:
  - In an interactive terminal (stdin and stdout are TTYs) and without `--yes`, it lists every harness with the detected and `--agent` ones preselected, noting which marker was found. The user toggles entries by number (space- or comma-separated) and confirms with Enter; an empty selection or an unknown number asks again. The prompt uses `node:readline/promises`, adds no dependency, and reaches the command as `Io.prompt`, which `bin.ts` sets only on a TTY, so tests drive it with scripted answers. Ctrl-C or end of input cancels with exit code 130 before anything is written.
  - Otherwise the selection is the detected harnesses plus `--agent`. If that is empty, it fails with a usage error that lists the names.
- `dld update` never prompts: it refreshes what is installed plus any `--agent`.
- An unknown harness name is a usage error that lists the valid names.
- Gemini CLI is not a named target. Its users get skills through the `.agents/skills/` layout, and the docs (workstream 10) explain adding AGENTS.md to its `context.fileName`.

## Rationale

- Harness names are what users know. The two layouts are an implementation detail, and the table is the one place that knows how each harness loads skills and rules.
- Detection with confirmation gives the right default without guessing silently. The flag path keeps CI and agents non-interactive.
- Failing on an empty non-interactive selection is safer than installing into directories no harness in the project reads.

## Consequences

- Adding a harness means adding a row, its markers and, if needed, an adapter or rule channel.
- Antigravity does not document whether it tells the agent a skill's absolute directory, which the `<skill-dir>` paths rely on. This is checked by hand in workstream 9 alongside the `npx skills` verification.
- The table reflects harness behaviour in September 2026 and needs revisiting as harnesses change.
