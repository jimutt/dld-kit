## Context

A run drives turns the user did not type, so the harness has to show what is happening — and show it well. Developer-facing visibility is a large part of why a harness extension is worth building at all: without it, a run is a wall of transcript that the user has to reconstruct in their head.

The obvious risk is over-drawing. `pi-goal-x` ships an expandable dashboard widget, and its recent history is dominated by fixing terminal damage it caused: a large, continuously updating widget wiped scrollback and pinned the viewport. `pi-goal-list-loop-audit` carries similar status complexity and a matching hardening history.

The wrong lesson to draw is "no rich UI". Pi offers four surfaces with very different costs, and only one of them carries that hazard:

| Surface | Cost | Nature |
|---|---|---|
| `setStatus` | one footer line | persistent |
| `setWidget` | redraws above the editor | persistent, and unbounded content is the hazard |
| `registerEntryRenderer` + `appendEntry` | none after render | scrolls with the transcript, TUI-only, outside LLM context |
| `ctx.ui.custom` overlay | none until opened | on demand |

## Decision

The run uses all four, matched to what each is good at.

**Status line** — always on while a run exists. One line: run slug, item position, current item status with decision IDs, elapsed against bound.

```
◆ payments 2/5 · DL-011 verifying · 34m/2h
```

**Widget above the editor** — the at-a-glance item list, at a **fixed height regardless of run size**. It shows a window around the current item: a little completed context, the current item, the next one or two, and a `+N more` line. It does not expand, and it has no interactive mode.

```
╭ dld-goal payments ─── 2/5 · 34m/2h ─╮
│ ✔ 1  DL-010         accepted  2m14s │
│ ▸ 2  DL-011 DL-012  verifying       │
│ ○ 3  DL-013         pending         │
│   +2 more                           │
╰─────────────────────────────────────╯
```

**Transcript cards** — rich per-item outcomes rendered as custom entries. Item started, accepted, blocked, and skipped each produce a card with its evidence: which checks ran, what they returned, which decisions moved to `accepted`. Cards are TUI-only and never enter LLM context.

```
✔ item 2 accepted · DL-011, DL-012 · 4m02s
  annotations  ok · 2 files
  npm test     ok · 18 passed
  review       ok · 1 moderate, fixed
  → DL-011 accepted · DL-012 accepted
```

**Board overlay** — `/dld-goal board` opens the full picture: every item, evidence per item, open and answered questions, and the event timeline. Opened deliberately, closed on Esc.

Notifications remain for transitions the user must not miss: a blocked item, a bound reached, a run completing.

The widget height is fixed at **five lines**: header, up to three item rows, and a `+N before · +N more` line when items fall outside the window. Height invariance is a unit-tested property (`render.test.ts` renders 3-item and 30-item runs and asserts identical line counts). Surfaces repaint on `session_start`, `turn_end`, `agent_end`, and after every `/dld-goal` command, and clear entirely when no run is active. Without a UI (print/RPC), nothing is painted.

## Rationale

Each kind of content sits where its cost is acceptable. Detail that a developer wants once — what exactly the checks returned — belongs in scrollback, where it is free to render, readable later, and diffable against the run log. Detail wanted continuously — where am I, how much budget is left — belongs in one or two lines that never grow.

The fixed-height widget is the specific protection against the pi-goal-x failure. That widget grew with content and expanded on demand; this one renders the same number of lines for a 3-item run and a 30-item run. Constant height means it cannot progressively consume the viewport no matter how long the run goes.

Entry renderers are the surface that makes rich output safe, and they are underused in the extensions surveyed — most push detail into widgets or raw messages. Cards also keep run detail out of LLM context, which matters for a loop whose whole purpose is spending context carefully.

An overlay for the full board rather than an expandable widget: same information, none of the persistent redraw, and Esc puts the terminal back exactly as it was.

## Consequences

Four surfaces is more code than one status line, and each needs its own tests. The widget in particular needs a test that its height is invariant across run sizes, because that property is the whole safety argument.

Card rendering duplicates information that is also in `events.jsonl`. Intentional: the log is for reconstruction, the cards are for reading while it happens.

A fixed window means the shape of a large run is not visible in the widget. The board covers that, and the agreed slicing is already written into the contract.

Terminal behaviour cannot be fully unit tested. The widget and overlay need manual verification against a real terminal, including a narrow one, before this is called done.
