## Context

A run drives turns the user did not type, so the harness must show what is happening. The temptation is a rich dashboard: item tree, evidence, timers, live progress.

The prior-art review found a concrete cost to that. `pi-goal-x` ships an expandable dashboard widget, and its recent history is dominated by fixing terminal damage it caused — a large continuously updating widget wiped scrollback and pinned the viewport. `pi-goal-list-loop-audit` carries similar status complexity and a matching hardening history.

## Decision

The run surface is a single status line, updated on state change only:

```
dld-goal payments · item 2/5 · implementing DL-011 · 34m/120m
```

It shows the run slug, item position, current item status with its decision IDs, and elapsed against the bound. When a run blocks it says so and names the question count.

No widget, no live-updating panel, no progress animation. Detail is available on request through `/dld-goal status`, which prints a table into the transcript where it scrolls normally and can be read back.

Notifications are used for transitions the user must not miss: a blocked item, a bound reached, a run completing.

## Rationale

A status line is one line of terminal state that pi already owns and manages. It cannot wipe scrollback because it does not draw over it.

The information a user actually needs while a run is going is small: is it moving, where is it, how much budget is left. Everything else is diagnostic, wanted occasionally, and better delivered as scrollable transcript output than as a panel competing for the viewport.

Updating on state change rather than on a timer keeps redraws proportional to real events.

## Consequences

Users who want continuous visibility must ask for it. `/dld-goal status` is a keystroke, and the event log is on disk.

A single line cannot show a multi-item tree, so the shape of a large run is not visible at a glance. Accepted: the run contract already documents the agreed slicing, and it does not change during the run.

If a rich surface is wanted later, it should be opt-in and tested against terminal behaviour, not only unit-tested.
