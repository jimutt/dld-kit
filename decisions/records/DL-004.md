## Context

A long-running loop must know when to stop and hand control back. Two cases matter: conditions that make starting unsafe, and failures that occur mid-run.

For the first, DLD has a specific hazard. `/dld-reindex` exists because parallel work produces colliding `DL-NNN` IDs, and resolving a collision renames decision files and rewrites annotations and cross-references. A run holds decision IDs and content hashes; a reindex invalidates all of them at once. Related preconditions — no config, a dirty tree, an already-active run — have the same character: the run cannot be trusted to mean what it says.

For the second, the surveyed extensions largely escalate badly. Some never pause at all and require the model to invent an assumption and continue, which compounds bad guesses over long runs. Others stop silently and leave the operator to reconstruct what happened from a transcript.

## Decision

**Preconditions, checked before a run starts and before a paused run resumes.** A run refuses to start when: `dld.config.yaml` is missing, the working tree is dirty, another run is active in this worktree, any targeted decision is missing or not `proposed`, or `find-collisions.sh` reports unresolved ID collisions against the base branch. If a collision appears mid-run — after a pull or merge — the run hard-pauses. The resolution path is always `/dld-reindex` first, then resume. The loop never works around a collision.

**Blocked items.** When an item fails its completion transaction, it retries once with the failure evidence added to the implementation context. A second failure marks the item `blocked` and pauses the run.

**Escalation is a question recorded in the run**, not a decision record: an entry in `events.jsonl` and a `blockedQuestions` entry in `state.json` capturing what failed, what was attempted, and the options. The operator answer is recorded the same way. While paused, the operator can answer and resume, skip the item (marked `skipped`, run continues), or stop the run.

If resolving a blocker requires a genuine design change, that goes through `/dld-decide` as a separate human step. The loop never authors decision records.

## Rationale

A blocker is operational — a check that will not pass, a conflict with existing code, a missing dependency. It is not a design choice, and writing it into the append-only decision log would pollute a permanent record with transient execution detail. The run log is the right home: same durability while the run lives, no lasting artifact.

One retry rather than none because the common failures — a missing annotation, a test that needed a fixture updated — are exactly what an agent fixes when shown the failure output. More than one retry mostly buys repeated variations of the same wrong approach, which the surveyed extensions all eventually built machinery to detect.

The loop is barred from authoring decisions because the decision log is the human record of intent. An autonomous loop inferring intent and writing it down inverts the relationship DLD exists to protect.

## Consequences

Runs cannot start on a dirty tree, which is stricter than `/dld-implement` and will occasionally be inconvenient. It is what makes the per-item diff attributable to the item.

A developer who ignores a hard-pause and forces a reindex mid-run will find the run unresumable — hashes and IDs no longer match. The run must be restarted from the new decision set. This is correct but should be documented clearly.

Skipped items leave decisions in `proposed` after the run reports complete. The run summary must call this out so it is not mistaken for a clean finish.
